# 构建记一笔与明细 UI

> **本文件是 change 的上下文入口。**
> 新会话只读这一份文件，就应当能还原本次改动的全貌，无需重新讨论。

## 为什么改

**背景（使用者原话与项目现状）**：

- 阶段 0 / 1 均已完成并归档，8 个 spec 模块、78 条 Requirement、94 个 Scenario；
  CI 全绿（run `43211076566`），产出约 21.6 MB 的 debug APK
- 使用者指令：「**开始阶段1**」→「按推荐来」→「**归档并开阶段2**」→「**按推荐来**」
- 但**应用目前仍只有一个占位页**，没有任何记账 UI。数据层再正确，用户也还没有
  一个能三秒记完一笔的入口
- 原始背景里最关键的两句：「**时间长了就没动力了**」、
  「**资产数据是高度敏感数据，不信任第三方**」。
  前者决定交互必须低摩擦，后者决定新增依赖不得夹带网络栈

**问题**：`reporting-ui` spec 早已写好「4 Tab + 中央 + 按钮」「记一笔保持低摩擦」
「明细分页」「组合筛选」，但都还没有落地代码。阶段 2 是数据层之后第一个
用户真正会打开的产物，也是「随手记」能不能坚持下来的分水岭。

## 做什么

1. 落 **4 Tab 导航骨架**：明细 / 资产 / 统计 / 设置 + 中央 `+` FAB；
   资产、统计放明确标注「阶段 3 / 4」的占位页，导航结构一次成型不返工
2. 落 **记一笔**：支出 / 收入 / 转账三 Tab、两级分类快选（一级可直接记、
   可选展开二级 chips）、内置 `BigDecimal` 计算器键盘、账户胶囊、日期、
   备注、「不计入收支」开关；编辑已有流水复用同一组件
3. 落 **明细首页**：当月概览（支出 / 收入 / 结余 + 左右切月）、
   **Paging 3** 按日分组列表、组合筛选面板、点击行编辑 / 删除二次确认
4. 落 **按日合计走 SQL 聚合**：日期头显示整月真实值，
   MUST NOT 用已加载分页数据求和（会随滚动跳变）
5. 落 **回收站恢复** 与 **设置页临时明文 JSON 导出**（兑现「每阶段跑一遍备份」）
6. 落 ViewModel + StateFlow、纯 JVM 计算器单测、版本查证记录

## 不做什么

- ❌ 资产看板真内容与余额调整记录 UI（阶段 3）
- ❌ 对账锚点、阈值分流、金额反查、疑似问题标记（阶段 3）
- ❌ 一级 / 二级环形图、下钻、月度趋势、年度双线（阶段 4）
- ❌ SAF 文件选择器、口令加密导出、CSV、应用锁、分类管理界面（阶段 5）
- ❌ v1.1 清单：模板 / 周期账、快捷方式与小组件、预算、退款报销、
  多币种混算、三级及以上分类、账单导入
- ❌ 不引入 `room-paging`、Vico、Coil / Glide、任何网络 / 埋点 / 上报 SDK
- ❌ 不改 `wzzhuz/my-app-workflow`、不改 `docs/设计规格书_v2.md` 历史快照
- ❌ 不在沙盒内编译 APK 或真机测性能（无 SDK / 模拟器）

## 对齐结论

> 阶段 0 在对话里产出，五项齐全才进入写作。

1. **要解决什么问题**
   把「随手记，时间长了没动力」变成真正能用的界面：三秒记完一笔、按日翻明细、
   几万条也不卡、漏记时能筛出来核对。这是数据层之后第一个用户会打开的产物。

2. **范围边界**
   - 改：4 Tab 导航、记一笔、明细首页 + Paging 3、组合筛选、回收站恢复、
     设置页临时导出、ViewModel / StateFlow、DAO 追加筛选与按日聚合查询、新依赖
   - 不改：资产 / 对账 / 图表真内容、阶段 5 功能、v1.1 清单、历史快照、my-app-workflow

3. **关键约束**
   金额铁律不破：计算器表达式 MUST 用 `BigDecimal` 求值，禁止 `Float` / `Double`
   参与，最终 `Cents.fromYuan`。明细 MUST Paging 3 + `localDate` 范围 SQL，
   MUST NOT `getAll()` 后内存分组；`PagingData` MUST 作为独立 `Flow`，
   **MUST NOT 塞进 `UiState`**（会 scroll-to-top），必须 `cachedIn(viewModelScope)`
   + 稳定 `itemKey`。按日合计 MUST 由 SQL `GROUP BY` 单独返回，不随分页跳变。
   统计口径复用 `StatRules`；配色按 spec 用红 = 支出 / 绿 = 收入。
   两级分类不得把「点两下记完」变成点四下。
   **本轮查证到的硬约束**：Compose BOM 2026.06 起不再通过 `material3` 传递
   `material-icons-core`，阶段 2 一用图标就会编译失败，必须显式声明图标 artifact（本轮最终锁定 `material-icons-core`）；
   Paging / Navigation 版本锁定与依据见 `design.md` 第 2 节。
   沙盒无 SDK / 模拟器，编译与单测由 Actions 验证；推送用单次 commit；
   Python 拼 Kotlin 后必跑五个检查脚本；不声明 `INTERNET`。

4. **验收标准**（可测）
   - **GIVEN** CI 跑完 **THEN** 五个静态检查 / 单测 / debug / release(lintVital)
     全绿，且 Actions 列表能查到该次运行
   - **GIVEN** 输入 `12.5+3×2` **WHEN** 保存 **THEN** 金额 1850 分且全程无浮点
   - **GIVEN** 选一级「餐饮」直接记 **THEN** ≤ 3 次点击完成且 `rootCategoryId = 1`；
     选「食材」则 `categoryId = 101, rootCategoryId = 1`
   - **GIVEN** 5 万条假数据 **WHEN** 切月 **THEN** 首屏走分页 SQL、无全量 inflate
     （本阶段以分页 SQL + 索引执行计划验证，真机耗时指标留到有设备时实测，不假报）
   - **GIVEN** 组合筛选设时间 + 账户 + 分类 + 金额区间 **THEN** 返回符合
     `StatRules` 口径的结果，已删除流水不出现
   - **GIVEN** 回收站恢复一笔支出 **THEN** 明细重现且余额重新扣减
   - **GIVEN** 阶段 2 结束 **THEN** 能从设置页导出一份含流水的 JSON 并重新解析

5. **被否决的方案**
   一句话结论：**所有「跳 change / 一次性做完资产统计设置 / `getAll()` 后内存分组 /
   `PagingData` 塞进 UiState / 计算器用 Double / `room-paging` 为每个筛选组合写
   @Query / 三级分类 / 设置做成第 5 个 Tab」的方案均被否决**，
   采用「自定义 PagingSource + 单条可选参数 SQL + 4 Tab 一次成型 +
   彩色圆 + 中文首字作分类图标」。完整表格见 `design.md`「考虑过的其他方案」。

## 影响范围

**触及的 spec 模块**：`reporting-ui`（主）、`ledger-transactions`（分页 / 筛选 DAO）、
`category-stats`（两级快选）、`reconciliation`（基础组合筛选）、
`backup-restore`（临时导出入口）、`build-and-ci`（新依赖与计算器单测）。

**是否需要重新安装包**：否（签名未变，数据库结构未变，无 Migration）

**是否会丢数据**：否（本阶段不改表结构、不改备份格式）

**行为变化**：项目从「有真实账本数据层但没有 UI」变为「可打开、可记一笔、
可翻明细、可筛选、可恢复删除、可导出备份」。

## 与项目铁律是否冲突

- [x] 不违反三条铁律（本轮兑现「记账不能变慢」与低摩擦）
- [x] 不涉及「已确认不做」清单中的功能
- [x] 无冲突

**补充说明**：上一轮对话里曾把导航说成「4 Tab + 首页右上角设置入口」，
与归档后的 `reporting-ui/spec.md`（4 Tab = 明细 / 资产 / 统计 / 设置，
设置 MUST NOT 作为第 5 个 Tab）不符。**以 specs 为真理源**，本 change 按 spec 落地。
阶段 1 归档时已修正旧统计口径的规格腐烂，本 change 基于干净基线写 delta。

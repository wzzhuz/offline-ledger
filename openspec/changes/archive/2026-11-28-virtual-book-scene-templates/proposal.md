# 第 94 批：虚拟账本从「礼金专用 UI」改成通用容器 + 场景模板

## 用户疑问（v0.2.72）

> 当前虚拟账本是通用能力还是固定的结婚礼金？通用能力却写死「记收礼 / 记还礼」
> 太死；固定能力的话，新增一条记录分类还要自己选。

**两个假设都成立**：容器是通用的（`VirtualBook` 只有 id/name/tag/archived/order），
皮肤和语义全是礼金专用；而且预填分类取的是「该 type 下第一个启用一级」——
点「记收礼」预填**工资**、点「记还礼」预填**餐饮**，每笔都得手动改掉，比自己选更别扭。

## 要解决什么

| # | 问题 | 处理 |
|---|---|---|
| 1 | 通用容器配礼金专用文案 | 新建 `VirtualBookTemplate`（人情往来 / 专项支出 / 自定义），按钮、汇总词、分段名、预填分类全由模板给出 |
| 2 | 每笔要手选分类 | 礼金模板内置 34004 / 9001；专项支出 / 自定义模板在设置页**设一次默认分类**，之后每笔自动带入 |
| 3 | 第 93 批漏收口的三处腐化文案 | 设置页「主账本明细默认不显示」「从左上角切换器进入」、codec/store 注释「据此排除台账记录」 |

## 一处技术口径调整（如实交代）

上一轮选项 2 推荐的是「把 9001 / 34004 随本批默认启用」。核查后发现：
`SeedCatalogTest` 硬断言「停用一级 = {学习娱乐, 人情社交}」，启用 9001 会连带
要把「人情社交」一级塞进快捷栏、改清单 v3→v4、三处一致性 + 单测 + 卸载重装，
代价远超收益。

改用**等价但零破坏**的做法：预填按分类 id 精确命中，只校验「存在 + 收支类型一致」，
**不要求 `enabled`**。保存校验（第 430 行）同样只查这两项，所以停用分类可正常
预填并落库。目标（不用手选分类）完全达成，且零改表、可直接覆盖 v0.2.72。

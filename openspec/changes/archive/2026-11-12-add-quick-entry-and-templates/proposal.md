# 模板、周期记账与桌面快捷方式（阶段 6a）

> **本文件是 change 的上下文入口。**
> 新会话只读这一份文件，就应当能还原本次改动的全貌，无需重新讨论。

## 为什么改

**背景（使用者原始诉求与项目现状）**：

- 使用者最初动机里最真实的一句是「**时间长了就没动力了**」——
  Firefly III 需要服务器或 NAS 长期开机，定时开机不方便随手记；
  市面记账软件又要把资产数据交出去
- v1（阶段 0–5）把账算准、数据锁住、报表做齐，
  出包阶段也交付了 `release.yml`（默认 R8，实测减少 24.9% 体积），
  **8 模块 / 137 条 Requirement / 212 个 Scenario、8 个已归档 change**。
  但每天仍要主动点开 App → 点 `+` → 选分类 → 输金额 → 保存
- `project.md` 的「已确认不做」清单把模板 / 周期账 / 快捷方式列为 v1.1，
  `reporting-ui`「v1 范围收敛」明确规定：要做这些
  **MUST 先显式更新 `project.md` 的「已确认不做」**。
  本 change 的第一步就是履行这道闸门，不是绕过它

**问题**：v1 解决了「能不能用」，没解决「愿不愿意长期用」。
固定支出（房租、工资、话费、订阅）每月重复手输，是「没动力」最直接的来源。

## 做什么

1. **履行闸门**：把 `project.md`「v1 明确不做（v1.1 清单）」改写为
   **「v1.1 分批计划」**，逐项标注 `6a 本批实现 / 6b / 6c 待决策 / 永久不做`。
   清单不删除，只按批次显式放行；三级及以上分类移入「永久不做」
2. **两张新表**：`record_templates`（可直接记一笔的模板）与
   `recurring_rules`（周期规则，自包含流水字段 + 排期参数）
3. **首次真正的数据库迁移**：`Migration(1→2)` 显式建表，
   `AppDatabase version = 2`，`DatabaseModule.addMigrations(*Migrations.ALL)`
4. **备份升级**：`BackupSchema.CURRENT = 2`、`MIN_SUPPORTED = 1`，
   payload 新增模板与规则列表；**v1 加密备份仍可导入**
5. **模板快选**：「记一笔」Dialog 顶部加常用模板 chips，
   点一下直接生成流水（不弹二次编辑），≤2 次点击记完一笔
6. **周期补记**：冷启动按日补记到期规则，幂等、批量单事务、
   60 天 catch-up 上限；**不用精确闹钟、不引入 WorkManager**
7. **桌面快捷方式**：静态 `shortcuts.xml`，点开直接进「记一笔」，
   且**不绕过应用锁**
8. **管理入口**：设置页新增「模板与周期记账」Dialog，不改 4 Tab 导航
9. 纯 JVM 单测覆盖排期计算、v1 备份兼容、Migration 契约；
   `check_transaction_annotations.py` 扩展写方法清单与迁移 SQL 检查

## 不做什么

- ❌ **6b / 6c 一律不做**：预算超支提醒、退款 / 报销成对模型、多币种、
  CSV 导出、账单导入、小组件、通知栏磁贴、三级分类
- ❌ **不改 `BackupEnvelope` 四项头部字段**（`BackupCounts` 只做带默认值的扩展）
- ❌ 不改 4 Tab 导航结构、不改既有「记一笔」表单与两级分类快选的交互
- ❌ 不改统计口径、金额铁律、余额重算唯一路径、`release.yml`、Manifest 权限
- ❌ 不引入 WorkManager / AlarmManager 精确闹钟 / 任何含网络行为的依赖
- ❌ 不用 `fallbackToDestructiveMigration`，不物理删除被引用的分类 / 账户
- ❌ 不把模板 / 规则塞进 SharedPreferences（那样换设备备份里没有规则）
- ❌ 不改 `docs/设计规格书_v2.md` 历史快照、不改 `my-app-workflow`

## 对齐结论

> 阶段 0 在对话里产出，五项齐全才进入写作。使用者确认「按推荐来」：
> 先归档出包阶段、只做 6a、闸门改写为分批计划表。

1. **要解决什么问题**
   回到「时间长了就没动力」：固定支出一键复用、周期账自动补、
   桌面直接进记一笔。从「能用」到「愿意长期用」。

2. **范围边界**
   - 改：`project.md` 闸门、2 张表 + DAO、`Migration(1→2)`、
     备份 `schemaVersion=2` 与 v1 兼容、模板快选、周期补记引擎、
     静态快捷方式、设置页管理 Dialog、写方法清单、纯 JVM 单测
   - 不改：6b / 6c 全部功能、导航格数、既有页面行为、统计口径、
     金额铁律、构建链、Manifest 权限、历史快照

3. **关键约束**
   **闸门**：`project.md` MUST 显式改写后才动代码；
   `reporting-ui`「v1 范围收敛」这条 Requirement **不改**
   （它描述 v1 的历史范围，仍然成立），本轮正是履行它 Scenario 里
   「需先显式更新 `project.md`」那一步。
   **事务**：模板 / 周期账生成的流水 MUST 走既有 `insertRecord` 同一事务
   与 `rebuildAllBalancesInternal()`，禁止新开一条写余额的路径；
   周期补记 MUST 一个事务内批量插入、末尾一次重算。
   **定时**：MUST NOT 用精确闹钟（Android 12+ 需 `SCHEDULE_EXACT_ALARM`），
   采用「冷启动按日补记」；**不引入 WorkManager**，零新增依赖，
   沙盒也无法验证后台任务。
   **迁移**：显式 `Migration(1→2)`；两张新表刻意**不声明 `@Index` / 外键**，
   让 Migration SQL 只需 `CREATE TABLE`，把 schema 校验不一致的风险压到最低；
   6a 不新增预置分类 / 账户，故 `migrate()` 不需要补 seed。
   **备份**：`MIN_SUPPORTED = 1`，v1 备份缺新字段时靠默认值解析成空列表；
   覆盖导入语义一致（v1 备份会清空现有模板 / 规则）。
   **低摩擦**：模板入口 ≤2 次点击；快捷方式点开直接进记一笔；
   不得因新功能增加两级分类快选的点击数。
   六个静态检查全过；推送单次 commit；沙盒无 SDK，编译与单测由 Actions 验证。

4. **验收标准**（可测）
   - **GIVEN** 闸门改写完成 **WHEN** 评审 change **THEN**
     `project.md` 明确标注 6a 本批实现、6b/6c 待决策，
     且「已确认不做」清单未被删除
   - **GIVEN** 建「午餐 35 元 / 餐饮·正餐 / 微信」模板 **WHEN** 从模板记一笔
     **THEN** ≤2 次点击、金额 3500 分、走同一事务且余额正确
   - **GIVEN** 每月 1 日房租规则 **WHEN** 隔 3 天冷启动 **THEN**
     补记 1 笔（不重复、不漏），`localDate` / `yearMonth` 正确
   - **GIVEN** v1 的 `schemaVersion=1` 加密备份 **WHEN** 用 v1.1 包导入
     **THEN** 全量一致、模板 / 规则为空、余额重算后净资产一致
   - **GIVEN** 全新安装与从 v1 覆盖升级 **THEN** 两条路径都能打开数据库
   - **GIVEN** 桌面点快捷方式 **THEN** 直接进记一笔而非首页；
     启用应用锁时仍 MUST 先解锁
   - **GIVEN** CI 跑完 **THEN** 六个静态检查、单测、debug / release 全绿
   - **GIVEN** 归档 **WHEN** 校验 specs **THEN** 无「v1.1 悄悄加回」矛盾要求

5. **被否决的方案**
   一句话结论：**所有「绕过闸门 / 七项全摊开 / 把 6b 塞进 6a /
   精确闹钟 / 自动生成流水绕过既有事务 / 破坏性迁移 /
   规则塞 SharedPreferences / 顺手做 CSV 或多币种」的方案均被否决**，
   采用「分批计划闸门 + 两张无索引表 + 显式 Migration + 冷启动幂等补记 +
   静态快捷方式」。完整表格见 `design.md`「考虑过的其他方案」。

## 影响范围

**触及的 spec 模块**：`ledger-transactions`（主，4 条）、
`backup-restore`（2 条）、`reporting-ui`（3 条）、
`privacy-security`（1 条）、`build-and-ci`（2 条）；合计 **12 条 ADDED**。

**是否需要重新安装包**：否。签名未变，但**这是首次数据库结构升级**，
从 v1 覆盖安装会执行 `Migration(1→2)`。

**是否会丢数据**：设计上否，但**迁移正确性沙盒无法证明**。
CI 只能验证编译与纯 JVM 契约；「从 v1 覆盖升级后数据还在」
必须使用者真机实测，不假报。

**行为变化**：多两张表、一次迁移、备份版本 2；
冷启动会按日补记到期周期账；记一笔多一排模板 chips；
桌面多一个快捷方式；设置页多一个管理入口。

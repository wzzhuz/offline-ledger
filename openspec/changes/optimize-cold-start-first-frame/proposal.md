# 冷启动明细首屏感知优先：启动快照 + 骨架兜底

> **本文件是 change 的上下文入口。**
> 新会话只读这一份文件，就应当能还原本次改动的全貌，无需重新讨论。

## 为什么改

**背景**：使用者在个人手机安装 R8 release `v0.2.30`，库内约 2000 条测试数据，未启用应用锁。
对照钱迹「几乎无感」的打开体验，本项目杀进程后冷启动到明细列表出现需要 1~2s。

**原始场景（使用者原话与实测，逐轮记录）**：

- 「记账项目 app 启动到首页显示明细列表需要 1～2s，和同类型应用钱迹对比体验差很多，钱迹感觉立马打开，几乎没感觉」
- 场景澄清：杀进程后的**冷启动**；**界面框架已出来、列表空着**（不是白屏 / 启动窗口慢）；装的是 **R8 release 0.2.30**；约 **2000 条流水**；**未使用应用锁**；「个人手机，认为是可信的」
- 对照观察：「首页详细页展示数据后切换月份，或者切换到统计页，账户页并不需要 1～2s，几乎是无感」——切月会重建 Pager 并跑三条月聚合，统计页 `init` 会跑几十条聚合，都无感
- 5 次冷启动实验：「基本都是 1～2s」——第 2 次起没有变快，排除「ART 自然攒 profile 后下次变快」这条缓解路径
- 数据性质：**测试数据，卸载重装无成本**（本轮方案零重装，此项不构成阻塞）

**问题**：慢的不是查询，也不是 SQLCipher 的页级加解密——切月 / 统计 / 账户页都跑在同一个**已打开**的加密库上，读的页照样要解密，却无感。
嫌疑收敛到「每次进程启动都必须重付一次的同步串行链」：
`System.loadLibrary("sqlcipher")` → Keystore IPC + AES-GCM 解密口令 → SQLCipher 开库密钥派生 →
Hilt 图首次构建 → Room 首次 open → 首屏 Paging 返回。
这条链里既有加密项（前三段）也有非加密项（后三段），**哪一段占 1~2s 尚未测量，不预埋结论**。

`openspec/specs/reporting-ui/spec.md` 写明「冷启动到明细首屏 < 1s」的性能基线（5 万条假数据 / 中低端机），
但 `docs/页面优化经验与避坑指南.md` §8 长期把「release 冷启动与 SQLCipher 开库」列为真机未验项。
本次 1~2s 是该基线的第一次真机信号，属于「基线未达成」，不是新功能需求。

**使用者对铁律 1 的重新澄清（原文口径）**：
> 「我最开始提的是数据不应该像钱迹一样默认上传第三方不可信服务器，现在手机 app 是自用，且装在个人手机上，加密是否有必要」

逐条核对 `openspec/project.md` 铁律 1 与 `privacy-security/spec.md` 后的结论：
红线是「默认把账本数据传到厂商服务器、且用户无法控制」，**本地加密不是这条红线**；
6c-1 已正式推翻「明文=风险」前提，但只改了导出文件那一半，本地库加密条款的理由仍停在「文件明文=风险」，
规格内部存在拧着的地方。然而现行 spec 有 3 条独立 Requirement（「本地数据库加密」「数据库以 SQLCipher 加密打开」
「数据库口令由 Android Keystore 保护」）把 SQLCipher 写成硬约束，去掉它属于改铁律 + 改 spec + 破坏性变更。
**本轮保留加密**，不借本次优化顺手改动；若将来要做，须单独决策并显式写进 `project.md`。

## 做什么

1. **先测后改**：把 5 点冷启动诊断打点作为第一个 task，测完再决定要不要追加自有 Baseline Profile 或开库后台预热，不预埋结论。
2. 新增独立的「启动快照」DTO 与 `noBackupFilesDir` 落盘，冷启动**不查库校验**快照。
3. 明细首屏改双源状态机：读快照 → 立刻渲染 → 与真实 Paging 并行 → `refresh` 转 `NotLoading` 后**一次性原子切换** → 销毁快照视图并用真数据覆写快照文件。
4. 定义快照判废条件（无筛选 / 默认月 / 月份一致 / db version 一致 / 已解锁）与骨架兜底；失败或超时降级骨架，不静默挂旧账。
5. 任一写库成功即作废缓存，挂在**最底层写事务出口**（现有 `DataRefreshBus` / `bumpRevision` / `refreshTick` 三套出口不统一，只挂一个必漏）。
6. 隐私与构建配套：补 `domain="file"` 排除规则、扩展静态检查、独立 DTO 不序列化 `RecordRow`、验 R8 下 kotlinx.serialization keep。
7. 启动期顺带减负（**非主方案**，实测已证伪查询是瓶颈）：去重 `refreshMonthCounts`、联想候选与月角标改首帧后低优先级预取、`applyDueRules` 挪到首屏稳定后。
8. 真机验收与活文档更新：把「冷启动首帧」从 §8 未验清单里结掉，新踩坑按「症状 → 根因 → 解法 → 防范」补记。

## 不做什么

- **不去掉 SQLCipher、不改 Keystore、不改数据库口令语义**（方案 A）；**不跳 KDF、不调 `kdf_iter`**（方案 B）。
- 不改表结构、不改 `AppDatabase.version`（仍为 5）、不写 Migration、**不要求卸载重装**、不丢数据。
- 不改统计口径、不改余额重算、不新增 / 不改 DAO 与 SQL 出口、不动备份 DTO、`SnapshotWriter`、CSV 导出、加密备份、自动快照。
- 不把启动快照做成长期第二数据源；**不在冷启动时查库校验快照**；**不绕过应用锁先渲染账目**。
- 不把 SplashScreen / 启动画面当主方案（症状是「列表空着」而非白屏，只改善打开感）；本轮不接启动画面。
- 不加小组件 / 通知栏磁贴（`project.md`「永久不做」）；不做全量内存分组（`reporting-ui` 禁止）。
- 本轮**不预埋 Baseline Profile**；若打点显示瓶颈落在非加密的类初始化段，作为条件性后续 task 单独加。
- 本轮**不改 `project.md`**：其中「稳定版前使用者至今未装机、只会用测试数据」的前提已被「已装 0.2.30、库内 2000 条测试数据」推翻，但本次不扩张范围，只在「关键约束」如实登记，留待单独决策。

## 对齐结论

> 阶段 0 在对话里产出，五项齐全才进入写作。写进这里是为了：下次会话不必重新讨论。

1. **要解决什么问题**
   杀进程冷启动到明细列表从空到有数据需 1~2s（R8 0.2.30 / 2000 条测试数据 / 无应用锁），对照钱迹几乎无感；
   目标对齐 `reporting-ui` 的「冷启动到明细首屏 < 1s」基线，该基线从未真机验过。
   **本轮采用感知优先**：不承诺缩短总时长，承诺「界面立刻可见」。

2. **范围边界**
   改：冷启动首屏双源状态机、一次性启动快照、失效与判废不变量、诊断打点、隐私/构建配套、启动期顺带减负。
   不改：加密与口令语义、数据库结构、统计口径、余额重算、导出与快照链路、四 Tab 骨架、明细既有筛选/切月/下钻行为。
   触及 `reporting-ui`（新增启动态行为 + 验收口径）、`privacy-security`（快照文件边界 + 不绕应用锁）、`build-and-ci`（R8 兼容与静态检查）。

3. **关键约束**
   - 三条铁律均不违反；铁律 1 按本次重读口径：红线是数据流向，本地加密非红线，但本轮保留。
   - 零改表 → 覆盖安装即可；使用者已确认是测试数据、卸载重装无成本，故破坏性方案本不受阻塞，但本轮不采用。
   - 快照 MUST 排在解锁之后渲染，MUST NOT 绕过应用锁；MUST NOT 进入任何导出 / 备份 / 快照 / CSV 数据出口。
   - 沙盒无 Android SDK / Gradle / 真机：不能本地编译，首帧耗时与「无空帧」必须真机验，**CI 全绿不得替代观感 / 性能验证**（活文档 §1 固定规则）。
   - 交付前 MUST 给出可点开的真实 commit sha + run id，按刚创建的 commit sha 逐文件比对 blob sha。
   - 实现时若用 Python 拼接 Kotlin 源码，MUST 跑 `scripts/check_kotlin_strings.py`（踩坑 1.1，已犯过两次）。
   - `project.md`「稳定版前未装机」前提已与实际状态不一致，本轮登记不改，未来若恢复显式 Migration 门禁须单独决策。

4. **验收标准**（可测）
   - 冷启动（杀进程后点图标）到**缓存首帧可见** < 200ms，同一台机同一 R8 包前后对比。
   - 真实首屏到达后的换源**无空帧**：缓存态与真实态之间不得出现 `LazyColumn` 空白帧。
   - 任一写操作成功后，缓存态立即退场，界面显示的是写后真数据，MUST NOT 残留旧账。
   - 判废 / 读取失败 / 超 3s：回退骨架，MUST NOT 静默显示过期账目。
   - 保留 `reporting-ui` 原 `<1s` 总基线（5 万条 / 中低端机），本轮不降低口径；5 点打点给出各段耗时。
   - 应用锁开启时，解锁前 MUST NOT 出现任何账目（含快照）。
   - `check_manifest_privacy.py` 与其余五个静态检查 PASS；release `lintVital` PASS；R8 包冷启动能正常反序列化快照。

5. **被否决的方案**
   一句话结论：A（去加密）/ B（跳 KDF）因「本轮感知优先、零破坏」不实施，靠 ART 自然攒缓存已被 5 次实验证伪，
   长期缓存 / 查库校验 / 绕锁先渲染违反一致性不变量，SplashScreen 与查询瘦身不解决「列表空着」；
   完整取舍表见 `design.md`「考虑过的其他方案」。

## 影响范围

**触及的 spec 模块**：
- `specs/reporting-ui/` —— 新增「冷启动首屏启动快照」「原子换源」「快照失效边界」「冷启动诊断打点」四条 ADDED；
  MODIFIED「性能验收基线」补入启动态判定，保留原 `<1s` 口径。
- `specs/privacy-security/` —— 新增「启动快照文件的本地边界」一条 ADDED；
  MODIFIED「关闭系统自动备份并排除数据库」补入 `domain="file"` 排除要求。
- `specs/build-and-ci/` —— 新增「启动快照 DTO 的 R8 兼容与静态检查」一条 ADDED。

**是否需要重新安装包**：否（零改表，`version = 5` 不变，覆盖安装即可）。

**是否会丢数据**：否。启动快照是可丢弃的渲染副本，不参与任何写入；删除或判废后回退骨架，真数据始终以 Room 为准。

## 与项目铁律是否冲突

对照 `openspec/project.md` 检查：
- [x] 不违反项目铁律
  - 铁律 1：账本数据仍不上传第三方、数据流向由使用者控制；快照只落本地私有目录并排除备份；JSON 备份已加密能力不倒退。
  - 铁律 2：不改金额、不改余额重算、不改统计口径唯一出口；快照只作渲染，不参与任何计算。
  - 铁律 3：本轮正是为「记账不能变慢」中的启动体验服务；不增加记账步骤。
- [x] 不涉及「已确认不做」清单中的功能（小组件 / 磁贴 / 云同步 / 账号体系 / 三级分类 / 跨币种混算等均未触碰）
- [x] 无冲突

**已知但不构成本次冲突的两处规格张力**（如实登记，不擅自改动）：
1. `project.md`「稳定版前未装机」前提已被实际装机推翻，本轮不改，留待单独决策。
2. `privacy-security` 本地库加密条款的理由（设备丢失 / 文件残留）与 6c-1「隐私边界是数据不离开设备」存在张力；
   本轮保留加密，若将来按使用者新口径调整，须走独立 change 改 `project.md` + 3 条 Requirement。

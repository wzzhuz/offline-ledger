# 设计（第 30 批）

## 根因
1. `SeedData` 把账户与分类写成 Kotlin 常量，首次建库灌表后虽是普通行，但**清单不可替换**、也没有启用态；「预置」与「用户数据」只有归档一套机制。
2. 交易对方是流水级自由文本，账单的商户全称与手工简称只能靠金额 + 时间窗猜，Q4 的疑似匹配因此偏弱。
3. 上一轮把 v0.2.14 的整组 commit / run / 制品编号当成落盘结果汇报，实际未执行；本批先把远端真实 HEAD 同步到本地再生成，所有编号只在推送后回报。

## 决策
- **A 方案（使用者 2026-11-18 拍板）**：代缴父母水电按「为谁付」归到人情，不按科目归到居住。居住从此是纯租房 / 自住成本；代价是「全年水电合计（含老家）」需跨两个一级手工相加，使用者原话是希望与租房费用区分开，按「本来就不想被加总」理解。
- **清单单一来源**：`assets/default_categories.json` 是运行时首选；`SeedData` 同构 fallback 仅用于 assets 缺失与纯 JVM 结构校验，`SeedCatalogTest` 逐行断言两者一致，防止两份清单漂移。解析用固定 schema 的极简正则，不依赖 android.jar 的 org.json。
- **enabled 语义**：复用归档之外的独立开关，但**不新增第二套隐藏机制**——停用不删行、不改历史；记一笔 / 筛选面板 / 预算 / 模板过滤，统计 / 排行 / 回收站 / CSV / 加密备份 / Firefly 映射仍读全量。否则合计一致性警告会炸。
- **月付归类**：花呗 / 白条 / 美团月付 / 抖音月付是信用支付，归 `LIABILITY`，不与支付宝余额、微信零钱并列；避免「花自己的钱」与「借钱花」混账。
- **对方归一（一期）**：只加 `counterparty_aliases(pattern → shortName)` 轻量表，导入落库前纯包含匹配；不拆 `records.counterparty_id` FK、不建对方管理页。拆表要动 16 条链路，自用场景边际收益不足，留二期。

## 消费方逐处核对（7 处）
| 消费方 | 本批结论 |
|---|---|
| 记一笔分类选择器 | 过滤 `enabled` |
| 筛选面板（rootOptions / childOptions / categoryOptions） | 过滤 `enabled`；显示名反查仍用全量 |
| 分类管理 | **不过滤**（否则停用的没法重新启用），加启用 / 停用菜单 |
| 统计占比 / 排行 / 历史 / 回收站 | 全量，硬约束 |
| 预算 / 模板分类选择 | 过滤 `enabled` |
| CSV 导出 / 加密备份 | 全量，带 `enabled`，重建后状态不丢 |
| Firefly III 映射建议 | 全量；映射到停用分类时允许「启用并新建」，不因停用失败 |

## 回退顺序
1. 若 `SeedCatalog` 解析在真机上失败 → `SeedCallback` 已写 fallback 到 `SeedData`，零数据损失。
2. 若 `enabled` 过滤导致历史筛选显示名找不到 → 保留显示名反查全量（已按此实现）。
3. 若商户别名误合并两家不同商户 → 归一表按 `pattern` 唯一、只做包含匹配；出问题清空别名表即回到原样，不动流水。
4. 若 v3 开库异常 → 按使用者口径卸载重装，先用 CSV 导出带走数据。

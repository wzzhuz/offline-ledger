## 0. 版本变更摘要（v1 → v2）

| # | v1 问题 | v2 处理 |
|---|---|---|
| 1 | 负债余额存负数，但资产页写「净资产 = 总资产 − 总负债」，必然算错 | 统一带符号余额，`净资产 = SUM(balance)`，展示层再拆分 |
| 2 | `balance` 为唯一真相源，无重算/自检，长期必然漂移 | 降级为可重建缓存，新增 `rebuildAllBalances()` 与启动自检 |
| 3 | 「零服务器」只是不写后端，未约束权限与系统自动备份 | 新增第 2 章隐私基线（无 INTERNET、关闭 Auto Backup、加密、应用锁） |
| 4 | 余额校准伪装成 EXPENSE/INCOME，污染明细与分类 | 独立 `BalanceAdjustment`，不参与收支统计 |
| 5 | 软删除过滤口径只在明细页写了一次，报表/导出可能漏 | 全局统一 `isStatRelevant` 口径 + DAO 单一出口 |
| 6 | 无对账能力，账实不符只能靠肉眼翻账 | 新增第 7 章：对账锚点、金额反查、组合筛选、尾差阈值 |
| 7 | 分类为单层 | 升级两级 + 冗余 `rootCategoryId`，统计支持大类/小类/下钻 |
| 8 | 未考虑 10 年数据规模与性能 | 新增第 9 章：万级记录估算、索引、分页、SQL 聚合、流式导出 |
| 9 | 技术栈多处「或」，AI 分阶段生成易前后不一致 | 全部定死，补充 Room 迁移、DI、TypeConverter、测试 |
| 10 | 备份放在最后一步，开发期数据无法保全 | 最小 JSON 导出提前到第 1 阶段 |
| 11 | 「个人/家庭」范围摇摆、币种/时区未定义 | v1 明确收窄为个人单币种，预留 `currencyCode`，冗余本地日期列 |

## 1. 项目定位与范围

**定位**：纯本地存储（Local-Only）、零服务器依赖、无广告、无网络权限、数据完全私有的原生 Android **个人**记账应用。

**核心目标（按优先级）**：
1. 三秒内记完一笔（决定能否长期坚持）
2. 钱算得准、账实可核对（决定能否信任）
3. 实时掌握净资产、月度支出大类构成、年度收支趋势（决定有没有用）
4. 数据出不去、且随时能带走（决定敢不敢用）

**v1 范围（必须收敛）**：4 个 Tab + 记一笔 + 资产与对账 + 月/年报表 + 加密 JSON 备份 + 无网络权限。

**v1.1 及以后**：模板/周期账、桌面快捷方式与小组件、预算与超支提醒、退款/报销成对模型、CSV 导出、多币种、账单导入、批量编辑。

> 定位为「个人」，不引入成员、多账本、共享账套。范围蔓延是个人项目烂尾的首要原因。

## 2. 隐私与安全基线（最高优先级，硬约束）

| 项 | 要求 |
|---|---|
| 网络权限 | **Manifest 中不声明 `android.permission.INTERNET`**。这是最硬的自我证明，也阻断任何依赖库偷偷联网。 |
| 依赖审计 | 禁止引入含广告、埋点、崩溃上报、网络统计的 SDK；每加一个依赖先确认无网络行为。 |
| 系统自动备份 | `android:allowBackup="false"`；Android 12+ 同时用 `dataExtractionRules` / `fullBackupContent` **显式排除数据库与备份文件**。否则系统默认把应用数据（含明文账本）备份到 Google Drive，与「不信任第三方」直接冲突。 |
| 本地加密 | 数据库使用 SQLCipher（Room 通过自定义 `SupportOpenHelperFactory` 接入），密钥由 Android Keystore 派生保管；或采用同等强度的库内加密方案。 |
| 应用锁 | BiometricPrompt / PIN，冷启动与从后台恢复时校验；`FLAG_SECURE` 防止最近任务预览泄露资产页（可开关）。 |
| 导出文件 | JSON 备份默认口令加密；CSV 默认关闭，导出前二次确认并提示「明文文件，勿放公共目录」。 |
| 最小权限 | 仅使用 SAF（系统文件选择器）做导入导出，不申请任何存储/读取权限。 |

> 监管导向上也支持本地优先：个人信息在技术可行时应优先在用户终端内存储、使用，且不应收集与服务无关的个人信息、不应调用非必要权限。

- 语言：Kotlin
- UI：Jetpack Compose + Material Design 3（禁止 XML 布局）
- 架构：MVVM + Clean Architecture（UI → ViewModel → Repository → Room DAO）
- 本地库：Room (SQLite) + SQLCipher
- 异步：Coroutines + StateFlow
- DI：Hilt（单模块个人项目足够）
- 序列化：`kotlinx.serialization`，**备份 DTO 与 Room Entity 分离**

## 4. 财务精度与一致性铁律

### 4.1 金额
所有金额字段（Entity / Domain / DTO）**必须为 `Long`，单位「分」**。仅 UI 展示与输入转换用 `BigDecimal` 处理字符串 ↔ Long，禁止任何 `Float` / `Double` 参与金额。

> 用整数分从根上消灭「1 分钱尾差」中的舍入类成因；剩余尾差只可能来自真实业务（手续费、汇率、漏记），交给第 7 章对账处理。

### 4.2 统一带符号余额（关键修订）
- 所有账户 `balance` 一律带符号：资产账户通常 ≥ 0，负债账户欠款为负（欠 500 元 → `-50000`）。
- **`净资产 = SUM(balance WHERE includeInTotal = 1)`**。删除「总资产 − 总负债」这个公式，避免负债取绝对值还是原值的歧义。
- 展示层再拆：`总资产 = SUM(balance WHERE type=ASSET)`，`总负债 = ABS(SUM(balance WHERE type=LIABILITY))`，仅用于显示，不参与计算。
- `creditLimit` 仅用于显示「可用额度 = creditLimit + balance」（balance 为负）。

### 4.3 余额是缓存，不是真相源（关键修订）
单一真相源 = `accounts.initialBalance` + 全部有效流水 + 全部 `BalanceAdjustment`。

`accounts.balance` 明确降级为**可重建缓存**：
- 唯一权威函数 `rebuildAllBalances()`：事务内按每条流水对账户的 `+/- amount` 聚合，叠加校准 delta 与期初，写回 `balance`。
- 任何流水/校准的新增、编辑、删除、恢复，都在**同一个 `@Transaction`** 内完成后调用 `rebuildAffectedAccounts(...)`；禁止在事务外单独改 balance。
- 冷启动执行一次全量重算并做账本健康自检（孤儿流水、`rootCategoryId` 与 `parentId` 一致性、校准记录合法性），异常时自动修复并写审计日志。
- 设置页提供「校验并修复余额」手动入口。

这样既保留列表读取速度，又具备自愈能力：事务保证单次原子，重算保证长期一致。

### 4.4 全局唯一统计口径
定义为常量，DAO/报表/导出共用一个出口，禁止各页面手写裸 SQL：

```
isStatRelevant = type IN (EXPENSE, INCOME)
              AND isDeleted = 0
              AND excludeFromStats = 0
```
`TRANSFER`、`BALANCE_ADJUST` 天然不计入收支。DAO 层只暴露 `activeRecords()` / `statRecords()` Flow，回收站与导出单独走明确命名的接口。

### 4.5 必测路径（单元测试）
insert / update / softDelete / restore / transfer / 信用卡消费与还款 / 校准 / 重算 / 导入后重算 / 两级分类统计合计一致性。§4 叫铁律就必须有测试。

| 字段 | 类型 | 说明 |

| `fromAccountId` / `toAccountId` | Long? | EXPENSE/TRANSFER 必填 from；INCOME/TRANSFER 必填 to |

| `note` | String | |
| `excludeFromStats` | Boolean | 报销/垫付等特殊流水 |
| `isDeleted` | Boolean | 软删除，回收站恢复 |
| `linkedRecordId` | Long? | v1.1 退款/报销成对关联，v1 先留字段 |

> 冗余 `localDate` / `yearMonth` / `rootCategoryId` 是性能与统计简化的关键：避免在 SQL 里对 `timestamp` 做函数计算导致索引失效，也避免多级分类的递归查询。

### 5.4 `balance_adjustments`（新增，替代 v1 的伪流水）
| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `accountId` | Long | |
| `deltaCents` | Long | 可正可负，直接叠加到账户余额 |
| `memo` | String | 「尾差校准」「对账差额」等 |
| `source` | Enum `MANUAL` / `IMPORT` / `RECONCILE` | |
| `timestamp` | Long | |

特点：**不参与收支统计、不进入分类统计、不出现在支出明细列表**；只在账户详情页折叠为「余额调整记录」并可撤销。撤销时同样触发 `rebuildAllBalances()`。

### 5.5 `trash`（建议，替代软删除）
v1 保留 `isDeleted` 亦可，但推荐改为「硬删除 + 归档到 `trash` 表」：回收站恢复时重新走 `insertRecord` 事务，天然解决余额重新联动，且主表不含无效行，所有查询不必再记得带 `WHERE isDeleted = 0`。若采用此方案，4.4 口径中的 `isDeleted` 可去掉。

### 5.6 索引（必须建）
```
records(localDate DESC, id DESC)              -- 明细分页
records(yearMonth, type)                      -- 月/年趋势
records(rootCategoryId, categoryId, yearMonth) -- 分类占比与下钻
records(fromAccountId), records(toAccountId)  -- 账户流水 / 余额重算
records(amount)                               -- 对账金额反查
categories(parentId)
```

## 6. 账务联动逻辑（Repository，统一 `+delta`）

所有账户一视同仁，**不再按 ASSET / LIABILITY 分支**：

| 操作 | 账户变动 |
|---|---|
| EXPENSE | `from.balance -= amount` |
| INCOME | `to.balance += amount` |
| TRANSFER | `from.balance -= amount`；`to.balance += amount` |

验证：信用卡消费 → 负债账户更负 ✓；信用卡还款（储蓄卡 → 信用卡转账）→ 储蓄卡减少、信用卡欠款归零 ✓；净资产在转账前后不变 ✓。

流程要求：
- 新增 / 编辑 / 删除 / 恢复，全部包裹在同一个 `@Transaction` 内，事务末尾调用 `rebuildAffectedAccounts(...)`。
- 编辑严格按「回滚旧 → 写新 → 应用新」三步，或直接「写新记录 → 全量重算」（更简单、更不易错，推荐后者）。
- 分类解析：写入 `records` 时由 `categoryId` 一并算出 `rootCategoryId`，写入后不允许分类树变更导致历史统计漂移（分类归档不改历史，改父级时按迁移策略批量更新 `rootCategoryId`）。

## 7. 对账与核对（新增，解决「差 1 分钱 / 差几十块」）

### 7.1 先区分两种「对不上」
- **A. 账实不符、账内自洽**：App 算出来 1000.00，实际 999.99。成因：漏记、手续费、汇率尾差、App 外自动扣款。→ 本章处理。
- **B. 账内不一致**：流水与余额对不上。→ 这是 bug，由 4.3 的事务 + 重算 + 自检修复，**不应让用户手动校准**。

用户的 Firefly III 场景属于 A：**目标不是找到那笔，而是让资产快照回到真实值，同时不污染收支报表**。所以校准不是「记一笔虚拟支出」，而是承认「这段历史不再追溯」，把差额作为期初/余额的调整量。

### 7.2 对账锚点（解决「账单太多、核算太费事」的根因）
每个账户保存 `lastReconciledAt` + `lastReconciledBalance`。每次对账成功后推进锚点，下次只需核对**锚点之后**的流水——把搜索范围从 10 年压缩到 1 个月。这是比普通筛选更关键的设计。

### 7.3 差额决策流程（资产页 → 账户详情 → 「对账」）
1. 用户输入**实际余额**（可从银行/钱包 App 复制）。
2. App 计算 `差额 = 实际 − 账面`，展示差额与锚点后的流水条数。
3. 分支：
   - **|差额| ≤ 阈值**（默认 1.00 元，可在设置里改，也支持按余额比例）：提供「**忽略尾差并校准**」一键按钮 → 生成 `BalanceAdjustment(deltaCents=差额, memo="尾差校准", source=RECONCILE)` → 重算余额 → 推进锚点。**不产生支出、不进报表、明细里不出现假消费**。
   - **|差额| > 阈值**：不强制校准，先引导核对，进入 7.4 的核对视图；找到后补记/修正流水；实在找不到再手动校准（备注必填，便于日后回看）。
4. 校准记录可撤销，撤销后余额自动重算。

> 小数额「不关注、直接抹平」是合理且专业的做法，v2 让它语义正确、可追溯、不脏数据，而不是伪装成一笔支出。

### 7.4 核对视图（明细页的「对账模式」）
普通「按分类/日期筛选」面对几万条仍然是大海捞针，真正有用的是：

1. **金额反查（最高价值）**：输入差额（如 38.50），一键筛出该账户下 `amount = 3850` 或 ±容差的流水，支持「等于 / 区间 / 近似」。差 1 分钱时立刻显示「无 0.01 记录」→ 说明不是单笔漏记，可放心校准。
2. **锚点切片**：默认只显示 `lastReconciledAt` 之后的流水，可手动放宽到近 7 / 30 / 90 天。
3. **组合筛选**：时间范围 + 账户 + 类型 + 一级/二级分类 + 金额区间 + 备注全文搜索；条件可保存为「筛选方案」。
4. **疑似问题标记**：同账户同金额短时间重复、异常大额、金额为 0、未分类流水，在列表项打小圆点，可一键只看疑似项。
5. **账户流水视图**：账户详情页按时间倒序展示该账户全部流水与余额变动，便于逐笔与银行账单对照。
6. v1.1 可选：导出该账户该时间段的 CSV 便于电脑比对。

### 7.5 明细页筛选常规能力
月份切换、类型/分类/账户筛选、备注搜索、金额区间——这些是基础，配合 7.4 的锚点与金额反查才构成完整核对能力。

## 8. 多级分类与统计（新增/改写）

### 8.1 模型
两级：`parentId` 自关联，`rootCategoryId` 冗余。流水的 `categoryId` 允许指向一级或二级（用户不想细分时可直接选一级），`rootCategoryId` 始终指向一级。

### 8.2 统计口径
- **按一级统计**：`GROUP BY rootCategoryId` → 一条简单 SQL，无需递归。
- **按二级统计**：`GROUP BY categoryId`。
- 校验不变式并在 UI 上提示：**一级合计 = 二级合计 = 总支出**（呼应「账要能对得上」）。
- 环形图/饼图支持层级切换：`按大类` / `按小类`。

### 8.3 下钻路径
一级扇区 → 展开该大类下二级构成（第二层环形或横向条形）→ 点二级 → 该分类明细列表（复用 7.5 筛选）。年度趋势图不受层级影响。分类明细表支持一级行展开/收起。

### 8.4 记一笔的交互不能变慢
一级图标网格 → 选中后展开二级横向 chips（「最近使用 / 常用」置顶）→ 直接记账。**必须保留「只选一级直接记」的快捷路径**，保证仍是点两下完成，不能因多级分类增加摩擦。这是留存红线。

### 8.5 备份兼容
备份 `schemaVersion` 升至 2；导入 v1 数据时所有分类 `parentId = null`、`level = 0`、`rootCategoryId = 自身 id`，历史流水 `rootCategoryId = categoryId`。

## 9. 数据规模与性能设计（新增）

### 9.1 10 年记录量估算
| 日均笔数 | 1 年 | 3 年 | 10 年 |
|---|---|---|---|
| 3（轻度，合并记账） | ≈ 1,100 | ≈ 3,300 | ≈ 11,000 |
| 5（中度，含通勤/三餐） | ≈ 1,800 | ≈ 5,500 | ≈ 18,000 |
| 8（重度，逐笔记） | ≈ 2,900 | ≈ 8,800 | ≈ 29,000 |
| 15（含转账/周期账/家庭） | ≈ 5,500 | ≈ 16,400 | ≈ 55,000 |

**结论：日常个人账本 10 年约 2 万～5 万条，是「万级」不是「千级」**（v1 回复中「几千条」是按 1–3 年估算，此处修正）。数据库体积约 10–20 MB，明文 JSON 备份约 10–15 MB，压缩后 1–3 MB。

### 9.2 会不会慢
**行数本身不是瓶颈**。SQLite 在手机上对 5 万行带索引的范围查询/聚合通常在十毫秒量级；真正会卡的是两件事：

1. 一次性把全部记录读进内存再在 Kotlin 里分组 → 几万个对象 inflate + 快照常驻，切月份/进场明显卡顿。
2. 每次进统计页都全量扫描聚合 → 重复计算。

### 9.3 对应设计（强制）
- **明细页**：SQL 按 `localDate` 范围过滤 + `Paging 3` 分页（每页 50–100 条）+ 索引 `(localDate DESC, id DESC)`；**禁止 `getAll()` 后再内存分组**。Compose `LazyColumn` 只渲染可见项。
- **统计页**：一律用 SQL `GROUP BY` 聚合，数据库只返回十几行结果；借助 `yearMonth` / `rootCategoryId` 冗余列走索引。年度趋势 = 12 行 × 收入/支出。
- **余额重算**：一条聚合 SQL 出全部账户（5 万行、十毫秒量级），结果缓存进 StateFlow，仅写操作后失效重算；账户数通常 < 20，不成问题。
- **导出**：协程 + 流式写入（逐条序列化写文件），禁止拼一个超大 String 再写出（OOM）；大文件先写临时文件再原子重命名。
- **无效行**：采用 5.5 的 trash 表方案，主表只增有效记录，避免软删除行长期堆积拖慢索引。
- **验收指标**（中低端机）：冷启动到明细首屏 < 1s；切月份 < 200ms；年报聚合 < 300ms；5 万条数据下分页滚动无掉帧。可用一次性生成的 5 万条假数据做性能自测。

## 10. 页面与交互（4 Tab + 中央 FAB）

底部导航 **4 个 Tab：明细 / 资产 / 统计 / 设置**；中央悬浮大号 `+` 触发「记一笔」（全屏页或底部 sheet），**不是第 5 个 Tab**。v1 规格书「4 个核心页面」却列到页面 5，此处收口。

**页面 1 明细（首页）**
- 顶部当月概览：总支出 / 总收入 / 结余，严格按 `isStatRelevant` 过滤，支持左右切月。
- 按 `localDate` 倒序分组，日头部显示当日支出/收入合计；列表项显示分类图标+名称（二级时显示「餐饮 · 食材」）、备注、账户、金额。
- **颜色修正**：中文语境用「红 = 支出 / 赤字，绿 = 收入」，或提供开关（v1 写反了）。
- 点击流水 → 详情/编辑/删除（二次确认）；顶栏提供搜索/筛选与「对账模式」入口（见 7.4/7.5）。

**记一笔**
- 三栏 Tab：支出 / 收入 / 转账。
- 分类两级选择（见 8.4）；转账为转出 → 转入选择器。
- 底部集成计算器键盘（加减乘除）、账户胶囊、日期时间、备注、「不计入收支」开关。
- 默认账户、默认上次分类、上次使用时间记忆，减少点击。

**页面 2 资产**
- 净资产看板：`SUM(balance WHERE includeInTotal)`；下方展示总资产、总负债（取绝对值显示）、各账户可用额度。
- 账户分组：资产账户 / 信用负债账户；点击账户进入详情（专属流水、余额调整记录、**对账**入口）。
- 账户管理：新增、改名、归档（禁止物理删除有流水的账户）、排序、是否计入净资产。

**页面 3 统计报表**
- 月度 / 年度切换；总收入、总支出、结余。
- 支出分类占比环形图：一级/二级层级切换 + 三级下钻（见 8.3）。
- 趋势图：月度 = 当月每日支出折线；年度 = 1–12 月收入 vs 支出双折线或分组柱。
- 所有图表原生 Canvas 自绘。

**页面 4 设置**
- 隐私：应用锁、`FLAG_SECURE`、导出加密口令。
- 备份与恢复：加密 JSON 导出/导入（SAF）、覆盖前警告、导入后 `rebuildAllBalances()`；CSV 默认关闭。
- 对账偏好：尾差阈值、默认筛选方案。
- 回收站：彻底删除 / 恢复（恢复走 insert 事务并重算）。
- 分类管理：两级增删改、排序、归档。
- 账本健康：一致性自检结果、手动「校验并修复余额」、审计日志。
- 基础：默认币种（v1 固定 HKD）、时区说明、v1.1 功能预告。

## 11. 备份与恢复（提前，格式先行）

- 格式：加密 JSON，`{ schemaVersion, exportedAt, currencyCode, accounts, categories, records, balanceAdjustments, trash }`；DTO 与 Entity 分离，Entity 加字段不破坏旧备份解析。
- 导出：SAF 让用户选保存位置（手机本地 / 自建同步文件夹），流式写入 + Gzip + 口令加密；导出前展示「将生成明文/加密文件」提示。
- 导入：**事务化**整包恢复，先校验 `schemaVersion` 与外键完整性，失败整体回滚；覆盖前二次确认；预置账户/分类的去重规则写死（按 id 全量替换 vs 合并，v2 定为**全量替换**并明确提示）；导入完成后强制 `rebuildAllBalances()` + 健康自检。
- CSV：可选，UTF-8 with BOM（Excel 中文不乱码），金额列输出「元」两位小数并注明导出即明文。
- **最小可用 JSON 导出必须在第 1 阶段就做完**：开发期表结构频繁变动，没有导出等于边写边丢数据。

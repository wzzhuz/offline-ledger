# 页面优化经验与避坑指南

> **状态：活文档**。这是「后续其他页面优化的参考输入」，不是历史快照。
> 与 `docs/设计规格书_v2.md`（不维护、冲突以 specs 为准）不同，本文件 MUST 随新踩坑持续更新。
>
> **适用范围**：任何 UI / 交互 / 布局 / 图表 / 表单改动，以及任何 CI、推送、归档动作。
> **来源**：初始设计 → 阶段 0–5 → 出包 → 6a/6b/6c-1/6c-2 → 10 批真机打磨（v0.1.0 → v0.1.7）的真实记录，
> 逐条可回溯到 `openspec/changes/archive/*/design.md` 与 `polish-device-experience/design.md`。
>
> **怎么用**：动手前读 §1 + §6.1；改 UI 时对照 §2 + §3 + §6.2；交付前跑 §6.3；归档时按 §6.4 + §5。

## 0. 四条压舱石

1. **状态要核验**——任何「已提交 / 已构建 / 全绿」的结论，必须由远端 API 证明，不凭上一条回复的记忆。
2. **UI 要分层**——「看着乱」和「看着空」往往是同一个病（信息层级没立起来），解法是降噪 + 定网格，不是塞内容。
3. **约束要可测**——设计判断一旦被真机打回，立刻写进 spec 的 SHALL / SHALL NOT，否则下一批一定会重犯。
4. **历史要留痕**——决策理由写进 `design.md`，过程状态写进 `tasks.md`，系统最终行为写进 `specs/`，三者不要混。

## 1. 状态与流程类：三次事故，换来一条固定开场

这是整个项目代价最高的一类问题，**优先于任何设计经验**。

| 事件 | 发生了什么 | 后果 |
|---|---|---|
| **「没做说做了」**（第 4 批） | 把对齐结论里「准备实现的内容」当成「已实现」汇报，编造了 run id 与 commit | 使用者下载发现和原来一样；核查后 run `43590734188` / `43590061274` 均 404、commit 不存在；真实跑的 release 是基于旧代码 |
| **「做了说没做」**（第 10 批） | 上下文丢失，回答停在「对齐门禁、仓库一行未动」，远端其实已完成改码 → CI → release → 坚果云 → 文档回填 | 使用者反过来提醒「0.1.7 我看已经生成了」 |
| **「没查当通过」**（第 8 批） | 上一轮文档 commit 的 CI 只说「查询时还在跑」，没回头核；实际是 failure | 把「未核实」包装成了「通过」 |
| **「做完没汇报」×4**（v0.2.0 / v0.2.2 / v0.2.4 / v0.2.5） | 上下文分段丢失，执行其实跑完了（改码→CI→release→坚果云→回填），但进展消息没带过来 | 使用者连续四次追问「没反馈进展」，只能靠远端 API 复核 |
| **「改完未推，被误判成没做」**（第 23 批） | 本地工作副本已改完 34 个文件（含 v2 表结构与全部增强），但执行停在推送前；状态核查只查了远端 HEAD，没同时比对本地副本，于是把「未推送」报成「没有可核验的落盘结果」 | 使用者重申口径后才继续执行；补规则：状态核查 MUST 同时查远端与本地差异 |
| **增量推送误删 `.github/`** | 推送脚本跳过点开头路径，误删 workflow 与 `.gitignore` | force-push 回原 HEAD；改用「不跳过点路径 + 误删保护断言」重建 |

### 固定规则（写死，不因赶进度跳过）

- **每轮开场**：先用 GitHub API 查 `HEAD commit sha`、最近 3 条 commit、`Actions runs` 结论与制品列表，再给状态。不许凭记忆说「当前版本 / 进行中 change / 上轮跑到哪」。
- **交付前**：用 Trees / Contents API 按**刚创建的 commit sha**（不是分支名）逐文件比对 blob sha，给出**可点开的真实 commit sha + run id**。
- **「查询时还在跑」必须回头核**，下一轮开场第一件事就是补查，不许留尾巴。
- **状态核查 MUST 同时查两处**：远端 HEAD / Actions **和** 本地工作副本相对远端的 blob 差异。
  只看远端会把「本地已改完、尚未推送」误判成「完全没执行」（第 23 批）；
  推送前必须跑「差异集合断言 + 零删除 + workflow/.gitignore 存在」三项。
- **产物名带版本号 + 短 commit sha**，禁止同名覆盖。第 4 批「下载和原来一样」的根因就是 `offline-ledger-v0.1.0-minified.apk` 每次覆盖，只有压缩包时间戳差几十字节。
- **CI 全绿 ≠ 验证通过**。真机观感、性能、弹窗、SAF、Excel 打开 CSV、R8 包启动，沙盒没有模拟器，必须显式列「未验证」，不许用编译通过代替。

### 推送与核验通道

| 坑 | 解法 |
|---|---|
| 逐文件 PUT Contents API 触发 **28 次 CI** | Git Trees API **单次 commit**（靠 `concurrency` 取消其余只是补救） |
| job logs / check-runs / artifact zip 返回 **403** | 临时在 workflow 加 `if: failure()` 把 Gradle 输出回传 `diag/`，读完后**步骤与文件都删除**；`GITHUB_TOKEN` 推的 commit 不触发新 workflow，不会成环 |
| `bash -e` 下 `grep -q ... && echo` 不匹配返回 1 → 整步失败 | 改 `if/else`；签名校验用 `apksigner verify --print-certs`，别用只认 v1 JAR 签名的 `keytool -printcert -jarfile` |
| 坚果云 | 必须用**应用密码**不是登录密码；产物文件名纯 ASCII；`permissions:` 同时写 contents + actions；`upload-artifact@v4` 带 `overwrite: true` |
| 版本号 / 文件名 | 每次出包递增 `defaultVersionName`，文件名带短 sha；metrics 制品名编码 `nsfalse` 等状态，绕开读不到 job logs 的限制 |

## 2. 设计判断类：最易反复横跳，改任何页面前先读

### 2.1 三次「降噪过头」→ **简洁 ≠ 砍易用**

| 批次 | 为了简洁砍掉的东西 | 真机反馈 |
|---|---|---|
| 第 5 批 | 最近收款方 chips、常用账户 chips | 「最近的几个收款方还是要展示，支出账户也显示几个常用的更方便」 |
| 第 8 批 | 输入框压到固定 48dp | placeholder 下半被裁、输入框与其他行不齐 |
| 第 9 批 | 48dp `TextButton` → 28dp 裸 `Text` | 「最近交易方偏小，容易误点」 |

**长期约束（已写进 spec）**：
- 可点击区域 **≥ 40dp**，不得以「简洁 / 降噪」为由压到 40dp 以下。
- 常用项采用「**平铺 4~6 个 + 更多弹层（带搜索）**」，不是全删也不是满屏平铺。
- 竞品（钱迹 / 随手记 / 鲨鱼）与 Material 规范共同验证的结构是「**统一表单行做骨架 + 快捷 chips 做加速**」，二者不冲突。

### 2.2 「空」和「乱」同根

6.73 寸上明细页「第一眼不整齐」和「比较空」是同一个病：**信息层级没立起来**。
解法是 **降噪 + 固定网格**（四列对齐、统一行高、细分割线代替卡片与阴影、中性色），
**不是**靠加迷你趋势图、卡片或色块把空白填满——那会把刚降下去的噪点加回来。

### 2.3 统一网格要做两半，只做一半等于没做

第 6 批统一了标签列宽（52dp）、左边界、细分割线，却漏了**行内容高度量级**：

| 行 | 容器 | 默认高度 |
|---|---|---|
| 输入 | `OutlinedTextField` | **56dp**（`OutlinedTextFieldDefaults.MinHeight`） |
| 快捷项 | `FilterChip` | **32dp**（M3 设计系统基线） |
| 最近项 | 裸 `Text + clickable` | **约 28dp** |

落差 28dp，一眼不齐。第 10 批把三类行收进 **32–44dp** 才算真正收口。
**改任何列表 / 表单页时，必须同时量「左边界」和「行高量级」。**
另注意：模板栏曾是全页唯一游离在网格外的顶层块——「同区域不混用」要逐块清点，不能只看前几行。

### 2.4 不要按位置 /  assumptions 猜默认值

`LedgerCurrency.DEFAULT = "HKD"`、`Asia/Hong_Kong`、SeedData 硬编码 `'HKD'`，是按「用户在香港」自作主张写的；
使用者实际在中国大陆，默认应是 **CNY + `Asia/Shanghai`**，且**设置入口根本不存在**。
两地同为 UTC+8、无夏令时，所以日期结果一直正确——**「没出 bug」不等于「假设成立」**。
默认币种、时区、语言、账户类型、初始账户，MUST 确认，不按 IP / 系统信息推断。

### 2.5 语义跟随类型，只在一处过滤

- **交易对方**：字段叫 `counterparty` 不叫 `payee`。支出显示「收款方」、收入显示「付款方 / 来源」、转账**整块隐藏**；转账仍可用备注。
- **分类候选**：按 `RecordType` 过滤必须写成**一个共用函数**。模板下拉、记一笔分类网格、转账 Tab 曾各写一遍，导致「支出能选收入分类」「转账显示收款方」「模板分类混乱」三处同源 bug 分三批才修完。
- **模板 = 预填草稿，不是固定账单**：金额每次都会变，MUST 可留空；点模板只填表单、不直接写库；所有字段仍可自由改；未填金额绝不能生成 0 元流水。周期规则会自动写流水，金额仍必填。
- **编辑态已有内容 MUST 可见可改**：把备注折叠进「更多」时，编辑旧流水要显示 `备注：xxx` 摘要，否则是回归。

### 2.6 层级、容器与状态作用域

- **金额独占一行**：360dp 宽度算下来能塞「金额 + 日期 + 时间」，但钱迹 / 鲨鱼 / 随手记三家都是「金额大字号独占一行、日期时间作下行小字」；同行会稀释键盘输入的视觉锚点，且 `99999.99` 这类长金额会挤压右侧导致截断换行。去标签 + 合并副行已够紧凑。
- **管理类 → 独立全屏页**（分类 / 回收站 / 模板 / 预算），**操作型浮层 → Dialog**（记一笔 / 筛选 / 口令 / 对账 / 下钻）。升页会增加导航深度，不要一刀切。
- **整行可点，不只点标签**：只把点击绑在「账户」两字上过不了三关——灰字标签视觉上是说明、TalkBack 不暴露 button 语义、约 32dp 远低于触摸目标。「账户 ›」整行可点既纳入标签又保住可发现性。
- **状态提升作用域**：筛选条件、`LazyListState` 曾随 NavHost destination 重建而清空，核对场景「补记一笔 → 去资产页看数额 → 回明细继续找」被迫重设。提升到 Activity 作用域解决。
- **图表**：收入 / 支出 / 资产量级差大时**共用 Y 轴会把小额线压贴底** → 每系列独立缩放；竖轴标具体刻度、点数值常驻峰值/末点/选中点、横屏全屏页铺开全量标签；**不跨币种混算**（6c-1 使用者明确拍板）。
- **图标与颜色**：6~7 种分类色一眼不清晰 → 中性单色圆 + 首字；方向语义色只留 支出红 / 收入绿 / 转账主题色 三种，不要重新引入彩色。`colorHex` 字段可保留供数据使用，仅 UI 不读。

- **浏览型长报表允许滚动**：第 11 批把筛选面板压到一屏是对的（操作型浮层「选完即走」），
  但第 13 批把这条经验错误外推到统计页，为「一屏塞下」把排行与环形图用切换 chip
  合并进一张卡，反而让边界变糊（第 14 批被使用者真机反馈推翻）。统计 / 洞察这类
  浏览型长报表天然允许滚动：**一卡一结论、边界清晰比省一次滑动重要**。
  MUST NOT 再以「一屏」为由合并卡片或用切换 chip 藏视图；只保证「总结 / 警告」首屏可见即可。

### 2.7 隐私边界别自己加戏（两次澄清，别再退回形式禁令）

**第一次（6c-1）**：曾把「导出文件默认加密」写成铁律，拿「明文 = 风险」拦 CSV。使用者澄清：
> **不可接受的是市场上 app 把数据存在他们服务器上；本地明文导出，数据掌控在自己手里就可以。**

**第二次（2026-11-17）**：又把「无 `INTERNET` / 零新增依赖」守成铁律。使用者再次澄清：
> **app 是自用的，自己不会主动往不可信的三方服务器上传。权限在自己手里就可以。
> 前面不用钱迹等 app 是因为它们默认就把数据上传到他们服务器、不支持用户控制。**

两次是同一条边界：**红线是「默认把账本数据回传厂商服务器且用户无法控制」，
不是文件形态，也不是权限/依赖的形式禁令**。判断顺序固定为：
① 会不会默认回传数据 → ② 用户能否控制数据流向 → ③ 是否传了账本数据本身。
三条都过，纯 UI 库、明文本地文件、`INTERNET` 权限本身都不构成违规。
当前 App 实际仍无 `INTERNET`（现有功能不需要），但**别再拿它否决纯本地能力库，
也别再拿「零新增依赖」拦 `reorderable` 这类 Apache-2.0 纯 UI 依赖**。
若将来真要联网能力，走 `project.md` 的「权限显式授权」闸门（用途 / 数据流向 / 用户控制方式），
静态检查已改为按授权放行；始终禁止的只有广告 / 埋点 / 崩溃上报 / 远程配置等默认回传 SDK。
已交付的口令加密 JSON 备份 MUST NOT 倒退成明文。

### 2.8 升级迁移：条件性暂缓，别拿它当否决理由

稳定版前只装过一次、只用测试数据 → 全新安装走 `onCreate`，`Migration` 从未在真机执行。
使用者明确：**出一个满意的稳定版前不会立即使用，数据结构完全不需要考虑升级迁移**。
- 因此不得再以「会破坏升级 / 要写 Migration / 旧备份读不了」否决数据结构调整。
- 已写好的迁移脚本与兼容测试**保留但冻结**，CI 门禁降级为记录性提示；写方法事务包裹与破坏性迁移禁令仍是硬检查。
- **恢复条件写死**：只有使用者明确说「需要考虑升级迁移」时才重新启用，并把覆盖升级加回真机清单。

### 2.9 「已确认不做」闸门

清单就是防功能悄悄回来的。阶段 5 它真的拦住过 CSV。
**不要为了省事整体删除清单或破例一次**——破例一次以后就失效。正确做法是把状态改成「本批实现」并保留其余项。

## 3. 技术类：症状 → 根因 → 解法 → 防范

| # | 症状 | 根因 | 解法 / 防范 |
|---|---|---|---|
| T1 | placeholder 下半被输入框裁掉 | `Modifier.height(48.dp)` 是**固定值**，小于「默认内边距 + 24dp 行高」 | 用 `Modifier.heightIn(min = 40.dp)`：**只降下限、不设上限**，内容自撑。官方明确 `MinHeight` 可用 `heightIn` 覆盖。**固定 `height` 已证伪，不得重试** |
| T2 | 输入框又比其他行大 | 第 9 批退回默认 56dp 修了裁切，却重新产生落差 | `heightIn(min = 40.dp)` + 联想行 40dp + chip 32dp，三类落进 32–44dp |
| T3 | 10 条 `e:` 编译错误、级联 `Unresolved reference 'it'` | 给 `String` 版 `OutlinedTextField` 加 `contentPadding` 命名参数；该参数只在 `TextFieldValue` 重载上，编译器套错重载 | 新增 M3 命名参数前 MUST 先确认属于哪个重载。`BasicTextField + DecorationBox` 更精确但要接管边框/焦点/清空，风险不值当 |

## 4. 校验器自己比被检查对象更容易错

归档与静态检查阶段反复出现**自误报**（`archive/*/design.md` 多处记录，口径不完全一致，至少 5 次以上）：

| 误报 | 根因 |
|---|---|
| 宽泛搜 `isDeleted = 0` | 把「**无需** `WHERE isDeleted = 0`」这类禁止性表述判成残留 |
| 宽泛搜 `BALANCE_ADJUST` | 把理由段「也不再是 records 的一种 type」判成残留 |
| Manifest 注释里的 `INTERNET` | 把说明文字当成声明了权限 |
| Migrations 注释里的破坏性迁移 | 同上 |
| 按**分支名**查 tree 报 `远端校验: FAIL` | PATCH ref 后有最终一致性延迟，拿到旧 tree；独立重算 blob sha 其实全 MATCH |

**规则**：
- 校验器只匹配**旧要求精确原文**，不宽泛搜子串。
- 按**刚创建的 commit sha** 查 tree，不按分支名。
- 任何 FAIL 必须走**第二条独立路径复核**，不许直接改被检查对象。
- 脚本半途抛异常时，**用远端基线重建本地再重跑**，不在半成品状态上续跑（否则 ADDED 会重复追加）。

## 5. 规格腐烂与规格债：避免 specs 里出现两条相反要求

| 事件 | 教训 |
|---|---|
| 阶段 1 归档时，旧「全局唯一统计口径」仍写 `isDeleted = 0`，而实现已改 trash 表 | 只追加 ADDED 不改旧 Requirement，specs 会同时存在矛盾要求 → **必须 MODIFIED 写出完整新文本并按标题整块替换** |
| 阶段 2 遗留「资产页显示阶段 3 占位说明」，阶段 3 修掉后又写「统计页显示阶段 4 占位」，阶段 4 再修一次（同一条 Requirement **三次 MODIFIED**） | **delta 里的 Requirement 只描述系统最终 SHALL 做什么**；「某页当前是占位」属于 `tasks.md` 的过程状态，不该进 `specs/`；理由段也别自称「不再绑定阶段号」而正文仍绑定 |
| 阶段 5 归档发现 CSV 在两处长期约束里一正一反 | 不是占位腐烂，是**两处长期约束相反**，要显式评审并统一 |
| 第 8/9/10 批内部改了行为（模板 4→6、默认高度→`heightIn`） | change **尚未归档**时，直接修订同条 Requirement 与其 Scenario，不新增叠加、不留矛盾文本、不新增 MODIFIED |
| 归档收尾脚本半途异常 | 见 §4 |

**归档校验清单**：每个 Requirement ≥1 个 Scenario、含 RFC2119 关键词（SHALL/MUST）、无重复 Requirement 标题、MODIFIED 按标题整块替换、ADDED 标题未在基线出现。

## 7.5 第 15 批：第三次外推——全站列表规范与排序作用域

- **统一网格其实有「三半」**：§2.3 写了「左边界 + 行高量级」，还差第三半
  **「行与行之间的边界」**。分类 / 模板 / 预算页压根不画分割线，回收站自己画 Box，
  资产页用 1dp 卡片间距，只有明细页有细线 → 视觉风格漂移。
  解法是 `ListDivider()` 单一来源 + 六页复用，**不是逐页调 padding**。
- **全站规范**：1dp / `Neutral 0.10` / 距屏幕 16dp；行高分档（明细 60 / 资产 56 / 管理 44）；
  可点区 ≥40dp。外层已带 12dp 的页面补 4dp 是务实取舍，写进 design，别当规范本身。
- **「排序点了没反应」先查作用域，别查动画**：`moveCategory` / `moveAccount` 都把
  **全部未归档记录**当一个数组交换，而 UI 先按 `type + level + parentId` /
  `AccountType` 过滤 → 交换发生在看不见的组之间。
  修法是按分组键重建全量 id 顺序再一次性写 `sortOrder`，DAO 与表结构一字不动。
  **同一类 bug 在两个 VM 里各有一份**，改一处时 MUST 全局搜同类写法（§7.2 再次应验）。
- **Compose 列表拖拽没有内置组件**：`dragAndDropSource/Target` 是跨应用 `ClipData` 协议
  （把图片拖进另一个 App），不是列表内换位；第三方 `reorderable` 库要新增依赖，
  社区还普遍踩「拖拽后 UI 不更新」（`mutableStateListOf` / 稳定 `key`）。
  零依赖做法：长按手柄 + `pointerInput { detectDragGesturesAfterLongPress }` +
  `draggedId` + `graphicsLayer` 位移 + 稳定 `key` + 松手一次性落库。
  **首版如实限制**：无实时让位动画、无边缘自动滚动，手感不如原生 `ReorderableListView`。
- **改代码前先查 spec 有没有把顺序写死**：`reporting-ui` 一条 Requirement 里列了
  「数据与备份 / 安全 / 偏好 / 账本 / 关于」，只调 `SettingGroupCard` 顺序会留下
  规格与实现相反 → MODIFIED 整块替换（§5 第三次应用）。

## 7.6 第 16 批：第四次外推——排序交互统一，以及「T12 例外」怎么判断

- **同一页面里「简洁」和「易用」的差别要按元素角色分**：资产页副信息（可用额度 /
  不计入净资产）本来就不点，`labelSmall` 没问题；但「详情 / 对账 / 编辑 / 归档 /
  删除」是**可点入口**，压到 `labelSmall` + 20dp 触摸区就必然被反馈「字偏小、点不中」。
  这是 §2.1 同一类违反的**第三次**。判断口径不是「整页统一字号」，而是
  **「这块要不要被手指点」**。
- **统一网格还有第四半：有没有底色容器**。第 15 批只补了分割线，没拆 `Card`；
  卡片内边距 + 阴影照样让内容比明细页小一圈。改页面时 MUST 连「行的背景」
  一起量，不能只看线、左边界、行高。
- **「自适应」要自适应的是容器，不是单个元素**：第 15 批把 chip 改成
  `widthIn(max)` 按文本收缩，但分行仍 `chunked(3)`，省出的宽度空在行尾。
  用户要的是「一行放几个由文本长度决定」→ 必须换分行算法（`WrapRow`），
  不是继续调 chip 宽度。
- **§3 T12 的例外条件（重要）**：T12 写「沿用 `Column + chunked(n)`，已转正组件
  也别为更优雅引入」，防的是**实验性 API 编译风险**。当反馈是真实布局缺陷、
  且替代方案用的是**稳定 `Layout` API** 时，可以换；但本批仍**刻意不用
  `FlowRow + @OptIn(ExperimentalLayoutApi)`**，因为 BOM 2026.06 的注解状态
  不确定。判断顺序：① 是不是真缺陷 ② 替代 API 是否稳定 ③ 是否零新增依赖。
  三条全过才换，且 MUST 在 design 里写明理由。
- **拖拽「生硬」的根因是重排时机，不是动画参数**：第 15 批 `onDrag` 只累加
  `acc`、`onDragEnd` 才一次换序 → 松手整列跳变。改成「每跨过一行立即更新
  `orderedIds`」，其余项就会实时让位。**订正（第 19 批）**：当时写「`animateItem`
  在 Compose BOM 2026.06 不存在」是**错的**——官方 Lazy lists 文档明确有
  `Modifier.animateItem()`（`LazyItemScope` 扩展，要求稳定 `key`）。
  首轮报 `Unresolved reference` 更可能是当时的列表是普通 `Column`（无 `LazyItemScope`
  receiver）或 import/作用域不对，不是 BOM 缺 API；别把一次编译错误写成平台限制。
  去掉后仍实时让位、只是没有补间动画；别在文档里写「动画已对齐」。
  Flutter `ReorderableListView` 的让位/阴影/边缘滚动是框架送的，
  Compose 零依赖实现 MUST 自己管稳定 `key`、
  拖动中列表重组、`onDragCancel` 回滚快照。
- **`@Composable` 调用点的作用域**：`LazyColumn { }` 的 content 是
  `LazyListScope.() -> Unit`，**不是 composable**；`item { }` 的 content 才是。
  `rememberReorderDrag` / `remember` 这类 MUST 放在 `@Composable` 函数体或
  `item { }` 内，放进 `LazyListScope` 会报「@Composable invocations can only
  happen from the context of a @Composable function」。
- **同一个 change 里出现两个同标题 MODIFIED 块是规格债**：第 14、15 批各写了一份
  「分类管理全量父级与排序」。本批不是再加第三份，而是**合并成一份**。
  归档前 MUST 检查 delta 内标题唯一性，否则归档校验会把两份都往 specs 里塞。
- **上移 / 下移不能全删**：TalkBack 用户无法执行长按拖动手势，Material 侧也建议
  提供替代按钮。统一交互 ≠ 删掉旧入口，而是把它降为兜底、不作为主入口。

## 7.7 第 17 批：父子手势竞争，以及「禁用滚动」不是终点

- **「拖动时屏幕跟着滚、拖拽被释放」是手势竞争，不是拖拽逻辑错**：
  父 `scrollable` 在 `PointerEventPass.Initial` 过 touch slop 拿到滚动权，
  子级手柄 `pointerInput` 在 `onDrag` 里的 `change.consume()` 是 Main pass，
  **拦不住 Initial pass**。父一开始滚 → 布局位移 → 子拖拽收 `onDragCancel`
  → `end(false)` 回滚顺序。修法是**拖拽期间禁用父滚动**
  （`verticalScroll(enabled=false)` / `LazyColumn(userScrollEnabled=false)`），
  不是多写几行 `consume()`。
- **别在 Initial pass 手动消费 down**：`detectDragGesturesAfterLongPress`
  内部 `awaitFirstDown` 依赖未被消费的 down；显式 consume 反而让拖拽直接失效。
  这是第 16 批「凭印象手写」类坑的镜像——**先确认框架内部怎么用事件，再动手**。
- **禁用滚动 MUST 与边缘自动滚动成对出现**：列表不止一屏时，禁用后手指拖不到
  屏幕外的位置，等于把功能改没了。`edgeDirection` + 每帧 `dispatchRawDelta`
  是零依赖做法；用 `onGloballyPositioned` 记录容器边界、手柄 root 位置 +
  `change.position` 换算手指位置，**48dp 是粗判定**，沙盒验不了手感，
  MUST 在 design 里写回退顺序（退 `NestedScrollConnection` / 阈值死区）。
- **`rowHeightDp` 估算值一定会错**：卡片根写 `heightIn(min=56.dp)`，内部却是
  「主行 + 副信息行 + 40dp 操作行」，实测 76–96dp；按 56 算跨行，手指没拖过
  一整格就换位。MUST 用 `onSizeChanged` 实测，且**只挂在单行根**——挂在
  含展开区 / 多行 chips 的整块 item 上会把整块高度当行高，错得更离谱。
- **「居中」有时不是写了居中参数，而是没写左对齐**：`layout(widest, ...)`
  让容器宽度取最宽行、剩余空间交给父级对齐策略 → 短 chips 行飘到中间。
  布局容器 MUST 显式声明 `horizontalAlignment` 并占满父宽，
  **留白在哪一侧要由代码决定，不能靠默认**。
- **同一个共享组件改一次，四处一起生效**：资产页是 `Column+verticalScroll`、
  分类与模板是 `LazyColumn`，竞争是同一类但容器不同。按 §7.2
  「老页面 MUST 全局搜同类写法」，不要只在报问题的那一页打补丁。
- **首次写「跨页面共享手势组件」首轮 CI 却全绿，靠的是两件事**：
  ① 动手前先把根因与三级回退顺序写进 `design.md`，把「哪里可能编译不过」
  提前列出来；② 推送前全局核对所有调用点（`rememberReorderDrag` 4 处、
  `WrapRow` 1 处、`CategoryRootRow` 新增参数 1 处）与函数签名。
  另外把 `onEdgeScroll` 从 `suspend (Float) -> Unit` 收敛成普通
  `(Float) -> Unit`（实际只调同步的 `dispatchRawDelta`），避免函数类型歧义。
  「凭印象手写」类坑已连续三批未复发，MUST 保持这个前置核对习惯。

- **三轮真机验不过就该换层**：第 15 批松手跳变 → 第 16 批实时让位无动画 →
  第 17 批长按窗口被父 `verticalScroll` 抢事件 → 使用者报「资产页拖动还是有问题」。
  连续三轮说明这是**平台级手势知识**（pointer pass 顺序、`enabled` 重组时序、

## §7.7 第 20 批：平台级手势不要死磕自研（外推四）

**触发**：第 15-18 批连续四轮真机验不过拖拽排序；使用者最终提出
「如果引入开源库呢」。查证后确认 `Modifier.animateItem()` 官方一直存在，
第 16 批把它记成「BOM 无此 API」是把 import / 作用域错误写成了平台限制。

**结论**：手势检测、pointer pass 顺序、长按窗口、`enabled` 重组时序、
边缘按距离变速滚动、让位补间，属于**平台级知识**，不是业务逻辑 bug。
连续两轮以上真机验不过，就应评估成熟库，而不是继续加 `consume()` /
`enabled` / 坐标近似。本项目引入 `sh.calvin.reorderable:reorderable:3.1.0`
后删掉约 2/3 自研代码，只保留「库 → 业务 id 映射 + 松手落库 + 分组语义」。

**边界经验**：

- 库不是一键替换：`onMove` 只给 `from/to`，不负责持久化、回滚、分组语义；
  必须写一层适配（本项目 `KeyedReorderState`）。
- 库 `onMove` 要求「返回前列表已更新」，所以拖动中 MUST 改内存顺序；
  落库 MUST 放 `onDragStopped`，否则等 layoutInfo 两帧直到超时。
- `Modifier.draggableHandle` / `longPressDraggableHandle` 是
  `ReorderableCollectionItemScope` 的**成员扩展**，MUST 在 `ReorderableItem`
  content 内先取出局部 `val`；内部 `Row {}` 会换 receiver，直接写会解析失败。
- `ReorderableItem` 的 key MUST 与父 `items(key=...)` 完全一致，用
  `"<prefix>-<id>"` 字符串便于 `LazyListItemInfo.key` 反解。
- 库的边缘自动滚动**只支持 Lazy 容器**；`Column + verticalScroll` 必须改
  `LazyColumn`，这正是资产页三年老结构的根因。
- 按行号做大块替换时，若前面刚改过 import 行数，行号会整体漂移，
  把函数签名 `) {` 一起替换掉 → 括号不平衡。MUST 用内容锚点或
  替换后立刻跑「去注释/字符串后的括号平衡」自检。本批首轮即踩此坑。

**依赖观（2026-11-17 使用者澄清）**：判断标准是「是否默认回传厂商服务器
且用户不可控」，不是「依赖数量」或「Manifest 是否出现 `INTERNET`」。
纯 UI / 本地库允许引入，新增依赖 SHALL 记录坐标、许可证与传递依赖审计；
广告 / 埋点 / 崩溃上报 / 远程配置 SDK 始终禁止。

**§8 版本继承**：v0.2.5（归档后基线 Req 227 / Sc 408）；真机未验清单新增「四处拖拽让位补间、拖到边缘连续滚动、
旋转屏幕后顺序保持」，原有 BiometricPrompt / SAF / Excel CSV / 5 万条切月耗时 /
横屏缩放继续继承。

## §7.8 第 22 批：真实样本推翻方案前提、零表结构迁移

**第一条：官方 issue / changelog 不能替代真实样本。** 前一轮依据 Firefly III 旧 issue
（「amount 全为负」「每 journal 只导一行，第二笔不导出」）拍板「split 合并成一笔」。
拿到 6.6.6 的 1916 行真实导出后发现：**已经带符号、每个 split 独立一行且各有
journal_id / 金额 / 描述 / 分类**，合并会凭空丢明细。改为按行逐条导入、组名写备注。
教训：涉及外部数据格式时，「按推荐来」的前提若被样本证伪，MUST 按样本修正并
在交付里明示，不能为了守着已拍板方案而将错就错，也不能偷偷改了不说。

**第二条：迁移类功能的「边界处理打包」不是打包，是同一事务里的一组语义规则。**

## §7.9 第 23 批：导入闭环、真实数据与「只加手势不改数据源」

**第一条：只加下拉刷新不改数据源，等于没做。** 导入写库后
`DetailViewModel._filter` 没变，`cachedIn` 的 PagingData 不会重查，
所以「切月份再切回来」才刷新。解法是「写操作发事件 → 订阅方立即重查」
与「下拉手势」两层一起做；只补手势，拉了也刷不出来。事件总线只发信号，
MUST NOT 把账本数据塞进事件。

**第二条：下拉手势只挂顶部窄条。** 父级 `pointerInput` 若挂整个列表会与
`LazyColumn` 争 pointer（第 17/18 批拖拽踩过同型坑）。

**第三条：图表配色与分类标识是两件事。** 列表 / chip 要降噪（中性单色圆），
扇区要区分度。自动生成分类的 `colorHex` 是同一个默认值，
`sliceArgb` 优先读它就全糊一块。按**分类 id** 取模分配色板才稳定，
按金额排名 index 分配会随占比变化变色。

**第四条：负值折线要改归一化，不是改颜色。** 收入−支出可为负，
原 `normalize` 会 `coerceAtLeast(0)` 把负值压到贴底。
必须换成 `[-max,+max] → [0,1]` 的有符号映射 + 居中 0 线，

**第五条：跨来源对账 ≠ 导入去重。** 同一格式导两次可用唯一键自动跳过；

**第六条：改表结构前先看库里是不是真实数据。** 前几批「大胆改、不考虑测试数据」
的口径适用于空库；第 23 批库里已有 1916 行迁移数据，

## §7.10 第四次外推：平台级手势一律优先官方组件（第 24 批）

**背景**：v0.2.7 为「导入后当前月不刷新」自造了 28dp 顶部窄条 +

直接点出正确形态：可滑动内容到顶（不能继续上划）后向下拉、过阈值松手、
刷新期间有指示器、结束给结果——这正是标准 Pull-to-Refresh。

**沉淀三条**：

1. **平台级手势不要自造**。下拉刷新用官方
   `androidx.compose.material3.PullToRefreshBox`（Accompanist `SwipeRefresh`
   已移除、官方明写迁移）；拖拽排序用 `sh.calvin.reorderable`（第 20 批已验）。

   引入前先问「这是业务逻辑还是平台手势」，前者自己写，后者找成熟实现。
2. **规范明确不要教手势的常驻文字**。刷新控件上的文字多半多余，要写就写
   「上次更新时间」这类有信息量的内容；那行小字本身就是自造方案的补丁味。
3. **insets 必须分层，不能整页套 `systemBarsPadding()`**。横屏下
   statusBars（侧边）+ navigationBars（底部）一起扣到 Canvas，最先被牺牲的
   永远是横轴标签槽。正确做法：顶部控制条吃 `statusBarsPadding()`，底部说明/
   标签槽独立吃 `navigationBarsPadding()`，绘图区高度用 `BoxWithConstraints`
   按剩余空间动态算，别写死 `chartHeight = 300.dp`。

**一条使用者偏好（长期约束）**：自用 App 不为「规范性」增加无用的业务按钮——
本批明确否掉 TopAppBar 无障碍刷新入口。注意这与 §2.1「可点区 ≥40dp」不冲突：
前者是「不新增控件」，后者是「已有控件别压小」。TalkBack 用户可退回已有的
明细页点击/编辑路径，不需要为一次性刷新多一个图标。

**导入闭环的通用形态**：长耗时写操作 MUST 有 `running` 态（「正在写入 N 条」+
进度）与 `result` 态（整页结果 + Snackbar + 显式完成入口），MUST NOT 只把确认
按钮置灰、MUST NOT 完成后自动跳走。结果视图要独立于 `message`，否则会被
说明文本或列表挤出视野——这是第 23 批「结果卡挂顶部」的教训。

## §7.11 第五次外推：状态流写回必须原子（第 25 批）

**背景**：第 24 批把导入结果做成整页 `when` 第一分支、也确实赋了
`fireflyResult = outcome`，真机却只看到「正在导入动画」。查证后是
`SettingsViewModel` 44 处 `_state.value = _state.value.copy(...)` 非原子写：
`confirmFireflyImport` 在结果赋值前先 launch `loadCategories()` / `loadAccounts()`，
这两个协程挂起后基于**旧快照**回写，把 `fireflyResult` 覆盖回 `null`、
`busy` 覆盖回 `true`。**状态机分支写得再对，状态被覆盖就永远进不去结果态。**

三条沉淀：

1. **StateFlow 写回一律用 `MutableStateFlow.update { st -> st.copy(...) }`**。
   禁用「读 `_state.value` → copy → 赋值」三段式；并发 reload / 事件回调越多越必现。
   lambda 参数显式命名（如 `st`），别用 `it` 遮蔽参数内部可能存在的 `it`。
2. **长耗时写操作状态机 MUST 有单一出口**：结果只在成功分支赋一次，
   `finally` 只兜底复位 `busy`；并重 / 重载放到结果赋值**之后**。
   失败也 MUST 出结果卡，不能只留一行 error 或停在转圈。
3. **「已实现」不等于「已验证」**。第 24 批汇报写的是代码意图，
   没核真机 `running → result` 转移；这是第 6 次状态事故（前五次见 §1），
   新形态为「把准备做的状态当已验证的结果」。交付前 MUST 追到可观测结果，
   不要把分支存在当成行为发生。

**资产页外推**：同一个官方 `PullToRefreshBox` 复用到第二个页面时，
刷新标志 MUST 与明细页 / 首屏加载三分离；自动刷新仍走 `LedgerApp` 的
`refreshTick` 通道，手动下拉只 `vm.reload()`，不重复发 `DataRefreshBus`
事件，否则双转圈。零第三方坐标、不加无障碍按钮的口径不变。

**UI 状态类改动 MUST 追到状态转移的终态，不能只追到代码落盘**。

## 7.15 预置数据语义、A 方案与商户归一（第 30 批）

- **清单与代码分离**：随包 JSON 是唯一可替换来源，Kotlin 只留同构 fallback；用纯 JVM 单测锁死两者一致，
  避免「改了 JSON 忘了改常量」。解析固定 schema 用极简正则，别在纯 JVM 单测里碰 android.jar 的 org.json。
- **enabled 不是第二套归档**：停用只过滤录入侧四处（记一笔、筛选面板、预算、模板）；分类管理必须显示全量，
  否则停用的没法重新启用；统计 / 排行 / 历史 / 回收站 / CSV / 备份 / FF3 映射一律读全量，
  否则合计一致性警告会炸。这是「改一处漏一处」最容易复发的一类，动手前先列消费方核对表。
- **按动机分一级，不按科目**：租房水电与代缴父母水电科目相同但动机不同；两级树不能加第三层时，

- **对方归一先做轻量一期**：只加别名表 + 落库前包含匹配，不拆 `records.counterparty_id` FK。

## §7.17 第 34 批：恢复闭环与两套 CSV 契约

**别把逻辑归因当源码结论**。门禁里推测「导出 CSV 与账单导入列名不同」，
真读 `CsvCodec` 才发现两者是同一套 11 列表头；失败在行级校验——
导出是全量流水（含 `TRANSFER`、无账户、无一级分类），
账单解析器只接受 `EXPENSE` / `INCOME` 且要求账户与一级分类非空。
动手前 MUST 读码确认，否则修的是想象里的 bug。

**SQLite 自引用外键是恢复的头号坑**。`categories.parentId` 自引用 +
`onDelete = RESTRICT` 时，`DELETE FROM categories` 逐行删不保证顺序，
先删父行就 1811；插入时备份数组也不保证父先于子。
正确做法：事务内 `PRAGMA defer_foreign_keys = ON`（提交时统一检查），
清空前 `UPDATE categories SET parentId = NULL`，插入按父先子后，
提交前 `PRAGMA foreign_key_check` 兜底。
**事务内 `PRAGMA foreign_keys = OFF` 是 no-op**，写了等于没写；
删 FK 约束更是把数据完整性一起丢掉。

**全量替换 MUST 覆盖所有表**。第 30 批新增 `counterparty_aliases` 后，
`importBackup` 没跟着加 clear 与 DTO 字段，恢复后残留旧规则、
`enabled` / `cardLast4` 回默认值。加表时 MUST 同步检查导出/恢复/清空三处。

**「导出」与「导入」不是天然互逆**。导出是给人看/给机器重建的全量快照，
账单导入是给第三方文件用的严格模板。MUST 按表头嗅探分流（不靠文件名），
给两个明确入口；跳过的行写 notices 而不是静默丢，也不伪装成错误。

**口令「可选」要先回答谁可读**。SAF 授权的是公共目录，文件管理器、
同步客户端、USB 拷贝、NAS 上有共享权限的账号都能读；
`hasFragileUserData` 只管卸载确认，不提供读保护。
所以口令仍必填，用 Keystore 加密存本机实现「免输」，
卸载即失效，文件本身永远加密。

## §7.18 第 35 批：导出格式 ≠ 重建格式，入口语义别互相打架

**一个入口两种语义，比没有入口更糟。** 第 34 批加了「从 CSV 重建」按钮，
却让确认流程继续调第三方账单的 `importRecords`（要求同名未归档账户 / 分类），
结果第 35 批使用者一点就报「账户不存在或已归档」。自有 CSV 只有 11 列流水，
**不带账户表与分类树**，所以它天生不能承担「清库 / 换机后的完整重建」；
那件事的正解是加密备份或自动快照。

更隐蔽的是**两处文案自相矛盾**：UI 帮助文本写「清库后请用从 CSV 重建」，
同一批 `CsvCodec` 注释写「完整重建请用从加密备份恢复」。使用者按 UI 点了，
没错，是文案骗了人。以后凡新增「导入 / 恢复 / 重建」类入口，必须把
**「这个入口吃什么、不吃什么、完整重建走哪里」** 三句写进同一处规格，
并在按钮、帮助文本、嗅探引导、结果摘要四处复读，不能只在代码注释里说对。

**缺项不是异常。** 严格行级校验适合第三方账单（错一行就该整批拒），
但回灌历史导出文件时，「当前库还没建这个账户」是常态：
逐项收集 → 跳过受影响行 → 结果摘要列清单 → 给可操作引导，
比首行抛异常再整批回滚有用得多。归档账户与停用分类尤其不能判成缺失——
它们只是「不再新选」，历史归属仍有效。

**纯 JVM 判定值得单抽一层**：`CsvRebuildResolver` 把「谁缺失」做成可单测的
纯函数，Repository 只负责执行，四条场景（归档不拒 / 空库全缺 / 换名清单 /
同名二级分父级）不用模拟器就能锁死，避免第 36 批又复制出分叉。

### 7.20 规则编辑器：别把「能力清单」做成「表单项清单」（第 37 批）

v0.2.18 底层 `RuleEngine` 已支持通用条件与多动作，UI 却只给了四个写死的输入框。
使用者反馈「非常死」——不是引擎不行，是**表单把引擎挡住了**。修法不是继续堆槽位，
而是把「字段 ▾ + 操作符 ▾ + 按类型分派的值控件」暴露出来，并用一个纯 JVM 目录对象
（`RuleEditorCatalog`）让 UI 与单测共用同一份枚举，杜绝「表单枚举与引擎枚举分叉」。

参考 Firefly III 三张截图时的三条取舍：

1. **别照抄超长单选**：FF3 把「字段 + 操作符」合成一个下拉，13+ 项文字被截断，
   还夹着 SEPA / 对账 / 日志 ID 等本项目没有的概念。两级短选择在 360dp 上才不挤。
2. **别照抄四列表格**：FF3 桌面端「条件 / 相反 / 值 / 停止处理」四列在手机上挤成一团；
   改卡片式动态行，上排选择器、下排值控件。
3. **值不该手打**：FF3 截图里「食-堂食」靠键盘敲；本项目 v0.2.14 换过分类清单，
   手打必然对不上名。分类 / 账户一律弹窗按 id 选（含停用与归档，显示「一级 / 二级」），
   对方 / 备注走 DAO 限量联想。

**字段映射比字段名重要**：FF3 的 `description` 是商户名/摘要 = 本项目「交易对方」，
`notes` = 本项目「备注」。认准这层映射，就不用为「描述」加一列改表。
「设置目标账户」也不能直译——本项目不建对方账户，映射成「交易对方改为」。

**入口归并**：分类调整不该是独立功能，它就是「条件=分类是 X → 动作=分类改为 Y」的一条
普通规则。独立映射表降级成编辑器里的「批量录入」（一次生成 N 条规则，共用同一
`RuleEngine` 与撤销链路）；删入口不删数据，此前生成的规则仍在 `rule_definitions` 里。

**安全护栏**：动态行默认给一条空条件时，`contains("")` 会命中全库；
加上「空关键词 + 空 ID + 空区间直接不命中」与保存前校验，
比靠使用者小心更可靠。

**平台级交互仍优先复用成熟实现**：本批没有新增第三方库，
值控件用 Material3 自带 `DropdownMenu` / `Dialog`，与第 20 批引入 `reorderable`、
第 24 批改用官方 `PullToRefreshBox` 是同一条判断。

### 7.21 列表、编辑器、执行入口要分开（第 38 批）

「保存的规则列表」和「规则编辑器」堆在同一滚动列，是典型的把三种职责塞进一页：
看清单、改定义、跑历史各要一次上下文切换。使用者反馈「列表和编辑器在一个页面不合理」，
本质不是排版，是**保存后的规则没有再次执行入口**——引擎里明明有
`previewRule` / `commit` / `revert`，却只在新建时勾「保存并立即应用」才够得着。

三条经验：

1. **拆页不必加路由**：设置内用 `rememberSaveable` 的 `page` 状态在三个独立
   `@Composable` 全屏页之间切，共用同一个 `ViewModel`，草稿不丢，也不用动 4 Tab 骨架。
2. **「预览」不是详情**：把按钮文案统一成「查看匹配记录」，只出现在应用流程里；
   改定义一律走「编辑」。两套语义混在一个词上，使用者会问「预览是看记录还是看规则」。
3. **入口跟着职责走**：规则从「数据与备份」里的一个按钮提为设置一级入口，排在
   「数据与备份」之后；旧门只删 UI 跳板，数据与已存规则一条不动。

**执行链路必须复用**：列表「应用」直接调既有 `previewRule` → `commit` → `revert`，
不新开写入口；`lastApplied` 只是内存态展示，不落表、不进备份 DTO。
这次只改编辑态与导航，`RuleEngine` 求值正确性是另一件事，别和拆页混着验。

## §7.22 第 41 批：年月选择优先用官方跳转能力，别把「零依赖」当默认答案

**触发**：明细页月份条与记一笔 DatePicker 的月份只能左右翻页；
筛选面板时间范围留空时，使用者问「是默认只筛当前月，还是因为按月展示」。

**先查证再选型**：上一轮门禁直接写「零第三方日期库」，是没查就定。
查完的结论分三层：
1. Compose M3 **没有**独立 `YearMonthPicker`；移动端 modal picker 的月份
   就是左右箭头 / 横滑，年份才点头部进网格 —— 这是官方设计，不是实现漏了。
2. **但官方已经给了跳转能力**：`DatePickerState.displayedMonthMillis`
   是可写属性，直接赋值即可跳到任意年月；日视图、闰年、无障碍全部继续用官方的。
   `setDisplayedMonth(YearMonth)` 扩展标了 `@RequiresApi(26)` +
   `@ExperimentalMaterial3Api`，写毫秒属性没有这两个限制。
3. 开源库确实存在（KEZ Lab compose-pickers 真有 `YearMonthPicker`），
   但它是**滚轮形态**、0.7.0 未到 1.0、29 stars；Sheets 是日期日历、
   Kizitonwose 只给月计算。都与「12 格一次点到」不一致。

**判断口径**：「优先用现成库」适用于**手势惯性 / 滚动物理 / 动画曲线**
这类平台级复杂交互（下拉刷新、拖拽排序都因此换过）。
「12 个月格 + 年份数字」是静态布局 + 点击，没有物理动画，自造不生硬。
真正复杂的日期渲染与校验，官方 DatePicker 已经做完了 ——
这次自造的是**选择入口**，不是**日期选择器**，两者不是一回事。

**时间语义的坑比 UI 更深**：`effectiveFromDate()` 在范围为空时返回
`MonthRange.of(yearMonth).first`，把「当前查看月」隐式注入成筛选条件；
`switchMonth` 又清掉 `fromDate/toDate`，切月丢筛选。使用者只能靠
「切月份试试」猜语义。修法不是加一行小字，而是让 `effective*` 返回
`Int?`，null 交给既有 `(:fromDate IS NULL OR ...)` 短路 ——
**单条参数化 SQL 不动、不新增出口、不碰统计口径**，
再用 `timeSummary()` 单一出口把语义明示在摘要行。

**新沉淀的规则**：
- 日期 / 年份类需求先查「官方有没有可写状态能跳转」，再谈造轮子或引库；
  能只补一层选择入口就别替换整套组件。
- 「范围留空」MUST NOT 静默等价于某个隐式条件；
  要么明示，要么用 null 短路，二者都要写进 spec 与 UI。
- 切月 MUST 保留筛选条件；「从选择器选中某月」与「左右箭头翻月」
  语义不同时 MUST 在 design 里写清，别混成一条。
- 12 个月命中角标 MUST 一条按年 GROUP BY 取回，MUST NOT 逐月全表扫描。

**§8 版本继承**：v0.2.23；零表结构（`version = 4`）→ 覆盖安装即可。
真机未验清单新增「年月 12 格一步跳转、记一笔月末 clamp、跨月摘要与双重夹击、
月格命中角标性能」，原有规则 / 备份 / 恢复 / CSV 重建 / 横屏缩放 /
release 冷启动与 SQLCipher 开库继续继承。


## §7.24 第 42 批（v0.2.24）：默认值也是契约，别把「能力具备」当「行为生效」

第 41 批把「不带时间查全库」的查询能力做出来了（`effective*` 返回 `Int?`、
SQL 用 `:fromDate IS NULL` 短路），却把 `allMonths` 默认留在 `false`，
还让 `selectMonth` 把「点月份」实现成「切回该月过滤并清掉时间范围」。
使用者看到的就是：不带时间仍只看当前月，空月要一个月一个月白翻。

三条教训：
1. **默认值就是行为契约**。「支持全部月份」和「默认就是全部记录」是两件事，
   把开关藏在快捷段里，等于把上一批的修复打折交付。
2. **定位与过滤必须拆状态**。锚点若写回主条件 Flow，`flatMapLatest` 会重建
   Pager、列表弹回顶部，「跳到那个月」反而失效；单独一个 Flow 只驱动滚动。
3. **交付前别擅自改判语义**。上一批门禁定的是「留空 = 全部」，落地时改成
   「默认按月但明示」，只在回报末尾补一句取舍——事后告知不是拍板，
   使用者下一轮立刻把这次改判退了回来。

月分组头非 sticky、不显示金额合计、锚点只对已加载项生效，三处都在
`design.md` 写明取舍，不伪装成「完整实现」。

## §7.25 第 43 批（v0.2.25）：FF3 description 独立字段

- **症状**：FF3 里 description 必填、常写「这笔干嘛的」，交易对方被当成占位维度（如「虚拟-不记录」）；导入后只剩对方与备注，看不懂交易内容。
- **根因**：v0.2.19/第 36 批把 FF3 `description` 误映射成「交易对方」、`notes` 映射成「备注」，本项目流水只有两个自由文本，丢的是整个维度。官方口径：CSV roles 里 description / note / opposing-name 是三列，notes 只在详情页可见。
- **解法**：`records` / `trash` 加独立 `description` 列（`version = 5`）；FF3 `description`→新列、`notes`→备注、对方占位名原样；自有 CSV 11→12 列（缺列按空串兼容）；BackupRecord 带默认值 + `schemaVersion` 升 5（旧备份缺键不炸）；记一笔加描述输入（placeholder-only）；明细行 `displayTitle` 动态回退（描述有值用描述、空着用对方）；规则字段目录加「描述」条件、联想与「描述改为」动作；筛选面板加「描述包含」并复用单条参数化 SQL。
- **硬约束**：MUST NOT 拼进备注、MUST NOT 覆盖对方；恢复仍走 `defer_foreign_keys` + `foreign_key_check`，加列不新增 FK 风险；描述可空、非必填；Top5 对方排行「虚拟-不记录」仍聚一坨是数据源占位习惯，不动统计口径。
- **取舍**：改表 → 卸载重装、先导出；FF3 CSV 导出本身不是备份，完整重建仍以加密备份/快照为准。

## §7.26 第 44 批（v0.2.26）：下钻带周期 + 转账编辑账户精确回填

- **症状**：统计页按月/年查看后跳转明细不带时间，只能看全部记录；转账编辑里冷门/归档的转出转入账户不显示，看起来像被换成了常用账户。
- **根因 1**：第 42 批把「不带时间 = 全部记录」设成全局默认时，三个跨 Tab 下钻工厂也写成 `allMonths = true`，统计周期上下文被顺手抹掉。属于「改一处漏一处」的默认值扩散。
- **根因 2**：ViewModel 其实已按 id 精确回填，是 UI 的 `filter { !isArchived }` + `take(4)` 把选中项挡在可见候选外，一排 chip 没一个选中就被误读。
- **解法**：`StatsDrillRange` 单一出口把周期固化成 fromDate/toDate，7 个下钻调用点共用；chip 显式写「来自统计」，只读展示名不进 SQL、不进 activeCount；账户快捷行合并选中项、归档可见标注、已删除保存前拦截。
- **硬约束**：明细页手工筛选「不带时间 = 全部」不回退；零新增 SQL 出口、零改表 → 覆盖安装；不动规则引擎、备份 DTO、统计口径唯一出口。
- **教训**：默认值一改，所有「全新构造」的工厂都要逐个复核；UI 的「可见候选」和 state 的「真实选中值」必须同时呈现，否则用户无法确认没被静默改写。


## §7.27 第 45 批（v0.2.27）：默认周期视图 / 编辑态置顶 / 交易详情页

## §7.28 第 46 批（v0.2.28）：切月即刷新 / chip 同行 / 系统返回消费

- **症状**：切月后详情页旁提示「该月记录尚未加载，继续下滑后再点一次」，列表也不刷新；月 / 年切换独占一行；在详情页左滑返回直接退出 App。
- **根因 1（最该记的一条）**：第 42 批把月份降为「只定位、不过滤」时 `locateMonth()` 只写 `_anchorMonth` 与 `_overview`，**漏写 `_filter.yearMonth`**；`effectiveFromDate()` 的 `periodBounds()` 永远按初始月份算。当时页面是「不带时间 = 全部记录」，缺口被掩盖；第 45 批改成无筛选按周期后立刻暴露。教训：**视图锚点一旦参与周期文案，就必须同步回写条件对象的周期字段**，否则「标题变了、查询没变」。
- **根因 2**：`actionRow` 二级页没走 NavHost，`OnBackPressedDispatcher` 不知道内部还有一层，系统 back 直接收 Activity。Compose 的 `BackHandler` 是官方现成出口，只消费事件，不接管返回动画、不拦 predictive back 预览。

- **不把实现做不到转嫁给用户**：「继续下滑后再点一次」本质是把刷新责任推给使用者。目标月无记录时列表为空、标题为该月，本身就是可见反馈；空月在 Picker 已灰显。
- **硬约束**：切月 MUST 只改 `yearMonth` + `revision`、MUST NOT 清空筛选条件；全部时间模式 `effective*` 仍为 null、月份不注入过滤；只读态左滑直回列表，编辑态「放弃修改」由编辑 Dialog 自身 `onDismiss` 负责，不在 `BackHandler` 叠第二层弹窗。零改表 → 覆盖安装。

## §7.31 第 49 批：冷启动「列表空着」用感知优先，不靠猜瓶颈

- **症状**：R8 release 0.2.30 / 约 2000 条测试数据 / 无应用锁，杀进程冷启动到明细列表出现 1~2s；钱迹几乎无感。界面框架已出来、**列表空着**（不是白屏）。
- **天然对照实验（使用者实测，比静态分析更值钱）**：首屏数据出来后切月份、切统计页、切资产页、开记一笔都无感；5 次杀进程冷启动「基本都是 1~2s」，第 2 次起没变快。
  - 切统计页跑几十条聚合、切月重建 Pager 都无感 → 排除「SQL 查询慢」「SQLCipher 页级加解密慢」；
  - 5 次稳定 → 排除「ART 自然攒 profile 后下次变快」；
  - 剩下的只可能是「每次进程启动必付一次的串行链」：`loadLibrary` → Keystore → SQLCipher 开库密钥派生 → Hilt 图 → Room open → 首屏 Paging。**加密项与非加密项仍叠在一起，未打点前不许定案**。
- **解法（感知优先，零破坏）**：不缩短那 1~2s 的 CPU 活，改成「界面立刻可见」。`noBackupFilesDir` 存一次性启动快照（最多 60 行）→ 冷启动先渲染 → 真实 Paging 并行加载 → `Loading→NotLoading` 后原子换源 → 换源即销毁快照并覆写。判废 / 失败 / 超 3s 回退骨架。`StartupTrace` 五点打点作为第一个 task，**测完再决定要不要加 Baseline Profile 或动加密**。
- **硬约束**：MUST NOT 把快照做成长期第二数据源、MUST NOT 在冷启动查库校验快照（等于重新串行等开库）、MUST NOT 绕过应用锁先渲染；三个内容源 MUST 是独立 `LazyColumn` 分支（Paging 3 refresh 会先清空 items，早切会把「列表空着」复现一遍）；零改表 → 覆盖安装。
- **失效出口的取舍**：门禁写「挂 `LedgerRepository` 最底层写事务出口」，落地改为 `init` 里注册 **Room `InvalidationTracker.Observer`**（11 张表）。理由：逐方法在 `db.withTransaction` 末尾加一行要改 42 处必漏，且 `check_transaction_annotations.py` 逐方法校验 `db.withTransaction` 字面，不能换成包装函数；数据库层通知覆盖面严格更大，含账户 / 分类 / 模板 / 规则等元数据写。偏差已写进 `design.md`「实现偏差登记」。
- **教训**：
  1. 「是不是加密导致」这个问题，用「切页面无感 + 连续 5 次冷启动」就能把答案从「可能是」推到「最可疑但未定案」；**先做零改动实验，别先付卸载重装的代价**。
  2. 「缓存一致性」不等于「让缓存永远等于数据库」；短命窗口 + 写入即失效 + 严格判废，比双源同步简单一个数量级。
  3. 隐私边界按使用者重读口径是「数据不默认上传厂商且可控」，**本地明文不是红线**；但 `allowBackup=false` + `domain="file"` 排除仍必须做，否则新副本会跟着系统备份走，恰好踩回最原始的红线。
  4. 改 UI 前先确认「症状是白屏还是空列表」：白屏用启动画面，空列表用首屏内容源，两者解药完全不同。
